# Сайт персональных приглашений

Статический сайт персональных приглашений. Каждое приглашение открывается по
собственной секретной ссылке вида `/i/<token>/`; корень сайта и любой неверный
путь отдают одну и ту же нейтральную заглушку. Сборка — один скрипт на Python 3
без сторонних зависимостей; результат (`dist/`) выкладывается на любой
статический хостинг.

Принципы, из которых исходит весь код:

- **только статика** — ни сервера, ни базы, ни форм; данные подставляются в HTML
  на этапе сборки;
- **приватность по построению** — страница содержит данные только своего гостя,
  со страницы нет ни одного запроса на сторонние домены, в заглушке и в
  служебных файлах нет ничего о событии;
- **прогрессивное улучшение** — весь текст приглашения виден без JavaScript;
- **разделение кода и данных** — в этом репозитории только код и вымышленные
  примеры; реальные данные, медиафайлы и конвейер выкладки живут отдельно.

Документ описывает репозиторий целиком: структуру, команды, формат данных,
шаблон, дизайн-систему и результаты приёмочных проверок.

**Если вы делаете стилизацию — начните с раздела
[6](#6-дизайн-система--раздел-для-этапа-стилизации)**; для запуска хватит
разделов [2.8](#28-тесты)–[2.10](#210-витрина-дизайн-системы).

```

fragments/             разметка секций, виджетов и плиток для include (в сборку не входит, раздел 4.7)
  sections/ widgets/   выбираемые по типу: имя файла = тип секции, виджета
  media/               плитки фото и видео

preview.html           страница-превью: обложка сайта, с которой сборка рисует картинку превью ссылки (не публикуется)

assets/

tools/
  gen_assets.py        иконка и нейтральная картинка предпросмотра из токенов
  _preview.py          картинка превью ссылки: обложка в headless Chrome (протокол отладки по каналу)
  build_examples.py    сборка примеров одной командой: медиа-заглушки, dist/<набор>/, ссылки на страницы
  gen_example_media.py медиа-заглушки для примеров по реестру медиа (для видео нужен ffmpeg)
  _schema.py           проверка данных (site.json и invitations.json)
  _page.py             дерево страницы гостя: что видно, тексты, даты, DOM-id
  _data.py             разбор JSON, пути полей, подсказки, id, тексты «ты/вы», токены
  _dates.py            русские даты и окончания событий
  _maps.py             ссылки на карты и адреса файлов
  _media.py            размеры картинок, сведения о видео, имена-хэши файлов
  _mp4.py              чтение заголовка MP4: размер, длительность, кодек, HDR
  _tokens.py, _png.py  чтение токенов и запись PNG (используются сборкой)
examples/
  data/                полный вымышленный набор: три события, места, фото и два ролика
  data-venue-pending/  набор без объявленного места и без медиа
tests/                 автотесты (unittest, стандартная библиотека)
.github/workflows/     сборка примеров и проверки на каждый push и pull request
```

Чего в репозитории нет и не должно появиться:

- **`dist/`** — результат сборки; создаётся командой `build` и перезаписывается
  целиком (в `.gitignore`);
- **`examples/media/`** — медиа-заглушки к примерам; генерируются командой
  `tools/gen_example_media.py` (в `.gitignore`);
- **любые медиафайлы** (картинки, видео, иконки) — без исключений;
- **реальные данные** — имена, даты, адреса, фотографии, адрес сайта.

Иконка сайта (`favicon.svg`) и картинка предпросмотра ссылки в репозитории тоже
не хранятся: иконку сборка рисует из цветовых токенов `app.css`, картинку
превью — **с обложки сайта** в headless Chrome (титульник: фото, имена, дата
основного события), а для сайта без обложки — нейтральную `og.png` из токенов
(см. [6.7](#67-иконка-картинка-предпросмотра-и-цвет-интерфейса-браузера)).

Реальные данные и медиа хранятся отдельно и передаются сборке параметрами
`--data` и `--media`; код о них ничего не знает.

## 2. Команды

Нужен **Python 3.10 или новее и Chrome или Chromium**. Python-зависимостей
нет: сборка и тесты используют только стандартную библиотеку. Браузер рисует
картинку превью ссылки — обложку сайта ([3.5](#35-своя-иконка-и-своя-картинка-предпросмотра));
без него `build` останавливается с подсказкой, отказаться от картинки можно
только явно (`--no-link-preview-image`). `validate` и тесты браузер не
требуют (тест с настоящим браузером пропускается, если его нет). `ffmpeg`
нужен единственному инструменту — генератору медиа-заглушек для примеров (и
при подготовке настоящего видео, раздел 8).

```
python3 build.py build    [--data DIR] [--media DIR] [--out DIR] [--site-name NAME]
                          [--chrome PATH] [--no-link-preview-image]
python3 build.py validate [--data DIR] [--media DIR]
python3 build.py token    [--prefix NAME]
python3 build.py links    --base URL [--data DIR]
```

| Параметр | Умолчание |
|---|---|
| `--data` | `examples/data` рядом с `build.py` |
| `--media` | `examples/media` рядом с `build.py` |
| `--out` | `dist` относительно текущего каталога |
| `--site-name` | переменная окружения `SITE_NAME`, иначе не задан (тега `og:site_name` нет) |
| `--chrome` | переменная окружения `CHROME`, иначе стандартные места: на macOS `/Applications/Google Chrome.app/…` и `Chromium.app`, на Linux `google-chrome`, `google-chrome-stable`, `chromium`, `chromium-browser` в `PATH` |
| `--no-link-preview-image` | переменная окружения `LINK_PREVIEW_IMAGE=off`, иначе картинка рисуется |

`--data` и `--media`, если заданы, считаются от текущего каталога.

### 2.1. `build` — собрать сайт

Проверяет данные и медиа, строит дерево страницы каждого гостя, рендерит
страницы, пишет календарные файлы, собирает `dist/` и проверяет готовый
результат (раздел 5). Сборка идёт во временный каталог рядом с `--out`
и подменяет `--out` только тогда, когда все проверки прошли: неудачная сборка не
оставляет полусобранного сайта.

`--out` перезаписывается целиком, поэтому скрипт откажется работать, если там
лежит не результат предыдущей сборки, а также если `--out` — корень файловой
системы, домашний каталог, каталог с кодом, данными, медиа или текущий каталог
(и их родители).

```
python3 build.py build --data data --media media --out dist
```

### 2.2. `validate` — проверить данные, ничего не записывая

Читает `site.json` и `invitations.json` и проверяет их по разделу 3: типы и
обязательность полей, **неизвестные поля (ошибка, с подсказкой «did you
mean»)**, повторы ключей, id и ссылки между реестрами, тексты и подстановки,
переопределения гостей. Затем строит деревья страниц — так выясняется, что
показано хотя бы одному гостю, — и проверяет медиафайлы только этих элементов:
наличие, регистр имени, символические ссылки, размер, тип содержимого,
сведения о видео. Шаблон не разбирается — это делает `build`.

В конце печатает счётчики:

```
validate: OK - 8 invitation(s), 3 event(s), 8 section(s), 12 media file(s) (data: …, media: …)
```

Сообщения имеют вид `<site.json | invitation #N>: field '<путь>'
<проблема>`, например:

```
error: site.json: field 'sections[4].widgets[0].events[1]' refers to an unknown event 'diner' (did you mean 'dinner'?); known: ceremony, dinner, brunch
error: invitation #3: field 'sections.<unknown key>' refers to an unknown section; known: cover, invite, personal, when, where, travel, story, rsvp
warning: site.json: media item 'story-3' is not shown on any page and its files are not published
```

Значения полей не цитируются никогда. Id из `site.json` печатаются, если
подчиняются правилу id ([3.7](#37-id--не-место-для-имён)). В записях гостей
ключ печатается, только если это имя поля формата или id, объявленный в
`site.json`; любой другой ключ — `<unknown key>`: ключ гостя может оказаться
именем. То же правило действует для повторов ключей в `invitations.json`.

### 2.3. `token` — новый токен приглашения

Печатает случайный токен (`secrets.token_urlsafe(16)`, 128 бит энтропии),
заведомо проходящий проверки раздела 3.

С параметром `--prefix NAME` печатает читаемый токен `NAME-xxxx`: хвост — четыре
случайных символа (`secrets`) из строчных латинских букв и цифр без легко
путаемых `0`, `o`, `1`, `l`, `i`:

```
python3 build.py token --prefix heron
heron-4tx9
```

Такой токен по-прежнему легко прочитать и продиктовать, а подобрать его по
словарю имён и прозвищ примерно в миллион раз труднее, чем голое `heron`
(почему это важно — раздел [3.3](#33-правила-токенов)). `NAME` — из тех же
символов, что и токен (`A–Z`, `a–z`, `0–9`, `_`, `-`), не длиннее 195; иначе
команда завершается с кодом `2`, значение в сообщении не повторяется.

### 2.4. `links` — ссылки для рассылки

Печатает строки «обращение → ссылка», разделённые табуляцией:

```
python3 build.py links --base https://example.org
Дорогая Кэрол!	https://example.org/i/0R-pnCqGFgrPOR5e-NluZw/
```

Это единственная команда, которая печатает персональные данные, поэтому она
**отказывается работать в CI**: если в окружении выставлена переменная `CI` или
`GITHUB_ACTIONS`, команда завершается с ошибкой и ничего не печатает. Ссылки
получают только вручную, на своей машине. Ничего не печатается, пока весь набор
данных не прошёл проверку.

### 2.5. Превью ссылки: `SITE_NAME`, без адреса сайта

Страницы приглашений несут теги превью ссылки ([4](#4-шаблон)): заголовок
«Приглашение · <имена пары>», описание из `linkPreview.description`
([3.8](#38-рецепты)), картинку и, если задано, **название сайта**
(`og:site_name` — мессенджеры показывают его над заголовком, без него — домен):

```
python3 build.py build --site-name "Приглашения"
SITE_NAME="Приглашения" python3 build.py build
```

Название — одна строка без управляющих символов, не длиннее 80 символов, без
`//`. Неверное значение `--site-name` — код 2, неверная переменная — код 1;
значение в сообщениях не повторяется, в журнале — только
`build: link preview site name: set` или `not set`. Пустая переменная — то же,
что её отсутствие. В заглушке тегов превью нет. При выкладке из CI название
удобно держать в переменной репозитория:

```yaml
env:
  SITE_NAME: ${{ vars.SITE_NAME }}   # пустая — тега og:site_name нет
```

Образец шага сборки для выкладки (GitHub Actions, `ubuntu-24.04`): Chrome на
раннере уже установлен, отдельного шага для картинки нет — её рисует сама
команда `build`; адрес сайта не передаётся.

```yaml
- name: Build the site
  env:
    SITE_NAME: ${{ vars.SITE_NAME }}
  run: |
    google-chrome --version
    python3 site/build.py build --data data --media media --out dist
```

Адрес сайта сборке **не передаётся никак**: все ссылки в мета-тегах превью —
пути от корня (`og:image` = `/assets/…`), `og:url` не выводится, абсолютного
адреса сайта в выводе сборки нет никогда (проверка результата отвергает любой
абсолютный URL в `<meta>`). Адрес страницы мессенджер знает сам — ему
отправили ссылку.

Риск: документация WhatsApp требует у `og:image` абсолютный адрес и называет
`og:url` обязательным, справочники по Telegram пишут, что относительные пути
не разрешаются. Поэтому карточка может прийти **без картинки** (заголовок и
описание остаются). Это проверяется на выложенном сайте
([11.1](#111-что-нужно-проверить-на-настоящих-устройствах), п. 5).

### 2.6. Медиа-заглушки для примеров

```
python3 tools/gen_example_media.py [--data DIR] [--out DIR] [--css FILE]
```

Читает `site.json` и создаёт ровно файлы его реестра медиа: фотографии, схему
проезда (картинку, которую место указывает в `directions`), фон обложки
(картинку из `background` обложки), постеры, картинки плиток (`thumb`) и
ролики. Каждый элемент — своего размера: `width`/`height` элемента, иначе
размер по роли (фон обложки — ландшафтный 2400×1600, ролик — вертикальный
720×1280, постер и картинка плитки — размера своего ролика). Картинки —
нейтральные плашки с сеткой и меткой кадра (видно кадрирование и
`object-position`); фон обложки — тёмный, со светлой сеткой и метками в углах и
в центре, чтобы были видны вуаль и выбранный `backgroundFocus`. Цвета — из
токенов `app.css`; на постере значка ▶ нет — его рисует плитка. Ролики
(`.mp4`, 5 с, тестовая таблица со звуком) и картинки `.jpg`/`.jpeg` требуют
`ffmpeg`; без него ролики пропускаются с предупреждением, код возврата
остаётся 0. Умолчания — `examples/data` и `examples/media`. Чтобы сразу
собрать примеры вместе с медиа, удобнее
[`tools/build_examples.py`](#29-локальный-просмотр).

### 2.7. Иконка и картинка предпросмотра отдельно от сборки


### 2.9. Локальный просмотр

Примеры собираются одной командой:

```
python3 tools/build_examples.py [--set data|data-venue-pending|all] [--out DIR] [--port N]
                                [--chrome PATH] [--no-link-preview-image]
```

Скрипт генерирует медиа-заглушки основного набора в `examples/media/` (в
`.gitignore`), собирает наборы в `dist/data/` и `dist/data-venue-pending/` (по
умолчанию оба) и печатает строки сборки, путь к сайту, команду просмотра
`python3 -m http.server -d dist/<набор> 8000` и адреса всех страниц с
обращениями (данные примеров вымышленные; в CI адреса и обращения не
печатаются). Основной набор показывает ролики, поэтому ему нужен `ffmpeg`: без
него набор не собирается, скрипт говорит об этом одной строкой и завершается
кодом 1, а набор без мест собирается всё равно. Принимаются только наборы из
`examples/`; ошибка аргументов — код 2. `--chrome` и `--no-link-preview-image`
передаются `build.py`: без браузера сборка набора падает с той же подсказкой.
Больше скрипт ничего не пишет:
`git status` после него пуст.

Свои данные собирают и смотрят так:

```
python3 build.py build --out dist
python3 -m http.server -d dist 8000     # http://localhost:8000/i/<token>/
```

Встроенный сервер на неизвестный путь отдаёт собственную страницу ошибки, а не
`404.html` — на хостинге отдаётся именно `404.html` (раздел 9).

### 2.11. Коды возврата и журнал

| Код | Что значит |
|---|---|
| `0` | успех |
| `1` | ошибка в данных, в шаблоне или в результате сборки |
| `2` | ошибка командной строки (неизвестная команда, отсутствующий или неверный параметр) |

Что печатается:

- **stdout** — только счётчики и пути: сколько приглашений, событий, секций и
  медиафайлов проверено, сколько страниц и календарных файлов записано, сколько
  файлов скопировано, откуда взяты иконка и картинка предпросмотра (у
  титульника — размер, вес, качество JPEG, окно и версия Chrome, но ни имён,
  ни дат), задано ли название сайта, итоговый размер. Нет браузера для
  картинки превью — ошибка с подсказкой и код 1. Если среди токенов есть короткие (меньше 12 символов), `validate` и
  `build` добавляют строку-сводку — только числа, без самих токенов:
  `validate: tokens: 23 (20 shorter than 12 characters, see README 3.3)`. Это
  не предупреждение и не ошибка, поэтому она в stdout; без коротких токенов её
  нет;
- **stderr** — предупреждения (`warning: …`) и ошибки (`error: …`), в конце
  строка вида `build: failed with N error(s)`.

Персональных данных в выводе нет — таково требование к коду и оно покрыто
тестами:

- приглашение в сообщениях называется только порядковым номером — позицией
  в `invitations.json`, считая с 1: `invitation #3`. Ни одного символа токена
  в выводе нет: токен может быть коротким и читаемым, и даже его часть — часть
  адреса чьей-то страницы. О дубле токена сообщается номерами обоих
  приглашений: `invitation #7: duplicate token (same as invitation #2; …)`;
- имя каталога медиа в путях заменяется на `<mediaDir>`, токен в путях — на
  `…` целиком, какой бы длины он ни был: `i/…/index.html` (и `I/…` — на
  файловой системе без учёта регистра это тот же каталог). Так же маскируются
  пути `--data`, `--media` и `--out` в строках журнала. Если `--out` по ошибке
  указывает не на прежнюю сборку, в сообщении об отказе вместо имён, похожих
  на токен (от 5 символов `A–Z`, `a–z`, `0–9`, `_`, `-`, без точки), стоит `…`,
  а внутри каталога `i/` (`I/`) скрыто любое имя; имена файлов видны;
- адреса сайта сборка не знает, название сайта (`SITE_NAME`) в журнал не
  пишется — только «set» / «not set»;
- значения полей данных не цитируются никогда — только пути к полям, имена
  полей, типы и id из `site.json`; ключи записей гостей — только если это имена
  полей формата или объявленные id (раздел [2.2](#22-validate--проверить-данные-ничего-не-записывая));
- имена медиафайлов в сообщениях о данных не печатаются: вместо них — поле
  (`media.walk.file`).

Переменная `BUILD_DEBUG=1` включает трассировку для внутренних ошибок. Она
предназначена для отладки на своей машине: в трассировку могут попасть значения
данных, поэтому в CI её включать нельзя.

## 3. Формат данных

Два файла в каталоге `--data`, кодировка UTF-8 (BOM допускается): `site.json` —
всё общее (секции страницы, события, места, программы, медиа) и
`invitations.json` — приглашения. Формат — **вторая версия**: в `site.json`
обязательно `"schemaVersion": 2`.

Проверка строгая:

- **неизвестное поле — ошибка** с подсказкой ближайшего известного имени
  (`unknown field 'coupleName' (did you mean 'coupleNames'?)`), чтобы опечатка
  не проходила молча;
- **повтор ключа** внутри одного объекта — ошибка: стандартный разбор JSON
  молча оставил бы последнее значение;
- `null` не принимается нигде: необязательное поле просто не пишут;
- пустая строка в необязательном текстовом поле равнозначна отсутствию поля.

**Данные первой версии** (поля `dateISO`, `dateText`, `venue`, `video`,
`schedule` в `site.json`, флаги `ty`/`vy`/`plusOne`/`outOfTown` у гостей) сборка
не читает: вместо разбора по полям она печатает одно сообщение на файл со
списком старых полей и ссылкой на этот раздел. Переносить их в новый формат
удобно по рецептам [3.8](#38-рецепты) — соответствие старых полей новым
подсказывает само сообщение об ошибке.

Как устроена страница:

- страница — **упорядоченный список секций** из `site.json`, секция — список
  **виджетов** (текст, дата, события, место, программа, медиа);
- события, места, программы и медиа описаны **реестрами** — объектами по id —
  и в секциях на них ссылаются по id;
- приглашение ничего не добавляет и не меняет порядок: оно только **включает
  и выключает** секции, виджеты и события и добавляет **приписки** к секциям
  и событиям. Скрытое вырезается **до** рендера: его нет в HTML страницы, в том
  числе ссылки на календарный файл скрытого события.

### 3.1. `invitations.json` — массив приглашений

| Поле | Тип | Обязательность | Правила |
|---|---|---|---|
| `token` | строка | да | см. [3.3](#33-правила-токенов) |
| `greeting` | строка | да | обращение, **одна строка**; без форм и подстановок |
| `form` | `"ty"` или `"vy"` | да | форма обращения для текстов с формами ([3.6](#36-тексты-формы-обращения-и-подстановки)) |
| `primaryEvent` | id события | нет | первостепенное событие гостя; по умолчанию — `mainEvent` из `site.json` |
| `events` | объект | нет | `{ "<id события>": { "visible": …, "note": … } }` |
| `sections` | объект | нет | `{ "<id секции>": { "visible": …, "note": …, "widgets": { "<id виджета>": { "visible": … } } } }` |

Переопределения — белый список, других полей нет:

- `events.<id>.visible` — показать гостю событие, скрытое в реестре
  (`"visible": false` там), или скрыть обычное;
- `events.<id>.note` — **приписка к событию**: выводится в карточке события в
  виджете «События» (например, «Напишите нам про аллергию»);
- `sections.<id>.visible` — включить секцию, скрытую по умолчанию, или скрыть
  обычную;
- `sections.<id>.note` — **приписка к секции**: карточка в конце секции.
  Секция с одной припиской и без виджетов тоже выводится — так устроена
  секция «Несколько слов лично» в примерах;
- `sections.<id>.widgets.<id>.visible` — включить или скрыть виджет; для
  этого у виджета в `site.json` должен быть `id`.

Правила:

- у гостя остаётся видимым хотя бы одно событие;
- первостепенное событие должно быть ему видимо; если `mainEvent` у гостя
  скрыт, `primaryEvent` обязателен;
- обложку переопределять нельзя — она одна на всех;
- приписка — строка, может быть многострочной; в ней работают подстановки, но
  не формы «ты/вы» (она и так пишется одному человеку);
- предупреждение, а не ошибка: приписка к скрытому у гостя событию или
  секции; приписка к событию, которое не показано ни в одном виджете «События»;
  включённая гостю секция, которой нечего показать.

Ключи в `events` и `sections` гостя — id из `site.json`. В сообщениях о записях
гостей печатаются только имена полей формата и id, объявленные в `site.json`;
любой другой ключ заменяется на `<unknown key>`: ключ мог оказаться именем.

### 3.2. `site.json` — общие данные

| Поле | Тип | Обязательность | Правила |
|---|---|---|---|
| `schemaVersion` | целое | да | ровно `2` |
| `coupleNames` | строка | да | одна строка; без форм и подстановок |
| `rsvpDeadline` | строка | нет | одна строка; нужна только текстам с `{rsvpDeadline}` |
| `mediaDir` | строка | да | имя каталога медиа, см. [3.4](#34-каталог-медиа-и-имена-файлов) |
| `mainEvent` | id события | да | основное событие; не может быть скрыто по умолчанию |
| `sections` | массив | да | секции страницы по порядку, не меньше одной |
| `events` | объект | да | реестр событий, не меньше одного |
| `locations` | объект | нет | реестр мест |
| `schedules` | объект | нет | реестр программ |
| `media` | объект | нет | реестр фото и видео |
| `texts` | объект | нет | общие тексты сайта — именованные переменные `{text:<id>}`, см. [3.6](#36-тексты-формы-обращения-и-подстановки) |
| `linkPreview` | объект | нет | `{ "description": "…" }` — описание в превью ссылки, одна строка на всех, см. [3.8](#38-рецепты) |

Ключи реестров — id ([3.7](#37-id--не-место-для-имён)).

#### Секции

| Поле | Тип | Правила |
|---|---|---|
| `id` | id | обязателен, уникален среди секций |
| `type` | `"cover"` или не задан | `cover` — обложка; без `type` — обычная секция |
| `visible` | булево | по умолчанию `true`; `false` — секция только для тех, у кого она включена |

**Обложка** (`"type": "cover"`): первая по порядку и не больше одной. Обложка
показывает имена пары (единственный `h1` страницы) и дату **первостепенного**
события гостя. Без обложки — предупреждение: у страницы не будет главного
заголовка. Обложка у всех гостей одна: переопределять её в приглашении нельзя.

| Поле | Тип | Правила |
|---|---|---|
| `eyebrow` | текст | подпись над именами пары, одна строка |
| `background` | id медиа | необязательное фото на фоне обложки, **только картинка** (видео — ошибка «must be an image»); под вуалью цвета обложки, см. рецепт [«Фото на обложке»](#38-рецепты) |
| `backgroundFocus` | `"center"` / `"top"` / `"bottom"` / `"left"` / `"right"` / `"top-left"` / `"top-right"` / `"bottom-left"` / `"bottom-right"` | какая часть фото остаётся видна, когда экран его обрезает; по умолчанию `center`; без `background` — предупреждение «has no effect» |

Фото на фоне — украшение: на странице у него пустой `alt`, поэтому медиа,
показанное **только** как фон обложки, не требует `alt` (предупреждения нет).
Файл фона больше 1 MiB — предупреждение: это первый экран.

**Обычная секция**:

| Поле | Тип | Правила |
|---|---|---|
| `title` | текст | обязателен, одна строка; формы и подстановки работают |
| `titleHidden` | булево | `true` — заголовок скрыт визуально, но остаётся доступным именем секции |
| `width` | `"narrow"` / `"wide"` | ширина колонки, по умолчанию `narrow` |
| `align` | `"start"` / `"center"` | выравнивание, по умолчанию `start` |
| `widgets` | массив | обязателен, может быть пустым |

Секция, в которой гостю нечего показать (все виджеты скрыты или пусты и
приписки нет), не выводится вовсе.

#### Виджеты

Общие поля: `type` (обязателен), `id` (нужен только чтобы гость мог включить
или скрыть виджет; уникален в секции), `visible` (по умолчанию `true`).

| `type` | Поля | Что выводит |
|---|---|---|
| `text` | `text` (текст, обязателен), `variant`: `body` / `lead` / `signature` (по умолчанию `body`) | абзацы текста |
| `date` | `event` (id; по умолчанию — первостепенное гостя), `countdown` (по умолчанию `true`), `calendar` (по умолчанию `true`) | дату и время события, таймер и кнопку «Добавить в календарь»; название события — если гостю видно больше одного события |
| `events` | `events` (массив id; по умолчанию — все видимые гостю) | карточки событий: время, описание, приписка гостя, место, программа; порядок всегда по времени начала |
| `location` | `location` (id, обязателен), `variant`: `full` / `compact` (по умолчанию `full`) | карточку места; `compact` — только название, адрес и кнопки карт |
| `schedule` | `schedule` (id, обязателен) | программу отдельно от события |
| `media` | `items` (массив id, не меньше одного), `layout`: `grid` / `ribbon` / `single` (по умолчанию `grid`) | плитки фото и видео; у `single` ровно один элемент |

Виджет даты и виджет событий показывают только видимые гостю события: если
событие, на которое указывает `date`, гостю не видно, виджет пропадает. Виджет
программы пропадает, если программа принадлежит только скрытым у гостя
событиям.

#### События (`events.<id>`)

| Поле | Тип | Обязательность | Правила |
|---|---|---|---|
| `title` | строка | да | одна строка; без форм и подстановок — попадает и в календарный файл |
| `location` | id места | да | место, которое ещё не объявлено, — место с `"ready": false` |
| `start` | строка | да | дата и время **со смещением**, см. ниже |
| `end` | строка | нет, но без него — предупреждение | позже `start`; на странице не показывается, см. ниже |
| `showEnd` | булево | нет | по умолчанию `false`; `true` — показать на странице интервал «16:00–23:30» |
| `schedule` | id программы | нет | программа события (в карточке) |
| `description` | текст | нет | многострочный — можно; формы и подстановки работают |
| `visible` | булево | нет | по умолчанию `true`; `false` — событие только для тех, у кого оно включено |

`start` и `end` — строгое подмножество ISO 8601: `ГГГГ-ММ-ДДTчч:мм[:сс[.мс]]` и
обязательное смещение (`+03:00`, `-05:00` или `Z`). Смещение обязательно: без
него таймер и календарный файл показали бы разное время в разных часовых
поясах. Пример: `2030-06-15T16:00:00+03:00`. Если у событий разные смещения,
сборка предупреждает: проверьте переход на летнее время.

Строки дат пишет сборка, по-русски и в смещении события: «15 июня 2030»,
«16:00», «Суббота, 15 июня 2030, 16:00».

**Окончание** (`end`) по умолчанию **на странице не показывается** — гость
видит только начало. Окончание нужно для трёх вещей:

- `DTEND` в календарном файле события ([5](#5-что-получается-в-dist-и-что-проверяется));
- пометки «прошло» и «идёт сейчас» в виджете «События»;
- выбор вкладки по умолчанию: событие, которое закончилось, уступает её
  следующему.

Чтобы показать на странице интервал («Суббота, 15 июня 2030, 16:00–23:30»),
событию ставят `"showEnd": true`. Без `end` флагу показывать нечего: сборка
предупреждает `field 'events.<id>.showEnd' has no effect without 'end'`.

`end` необязателен. Без него окончание — **начало плюс шесть часов**, одинаково
для всех гостей и везде (календарь, пометки, выбор вкладки), и сборка
предупреждает: `field 'events.<id>.end' is not set: the calendar and the
past/now marks use start + 6 h`. Окончание события не зависит от других
событий: соседнее событие его не сокращает, даже если начинается раньше.
Поэтому лучше задать `end` явно.

**Первостепенное событие** гостя (`primaryEvent`, по умолчанию `mainEvent`)
определяет дату на обложке, виджет даты без `event`, таймер и значения
подстановок `{eventDate}`, `{eventTime}`, `{eventTitle}`, `{eventPlace}`; в виджете
«События» его карточка выделена рамкой.

#### Места (`locations.<id>`)

| Поле | Тип | Правила |
|---|---|---|
| `ready` | булево | по умолчанию `true`; `false` — место не объявлено: карточка «Подробности появятся на этой странице позже.», остальные поля не выводятся |
| `name` | строка | одна строка; обязательна, если место объявлено |
| `address` | строка | одна строка |
| `description` | текст | многострочный — можно; формы и подстановки работают |
| `geo` | объект | `{ "lat": число, "lng": число }` — оба обязательны внутри |
| `maps` | объект | где место на каждой карте: идентификатор или текстовый запрос (таблица ниже) |
| `photos` | массив id медиа | фото и видео места (лента в карточке) |
| `directions` | id медиа | схема проезда, только картинка |

- `lat` в пределах ±90, `lng` — ±180. **`lat: 0, lng: 0` считается «не задано»**
  (это плейсхолдер, а не место в Атлантике);
- **кнопка карты выводится, только если место задано в `maps` именно для этой
  карты** — идентификатором или её собственным запросом. Одних координат для
  кнопки мало: у места только с `geo` кнопок карт нет, а если место не задано
  ни для одной карты, нет и всего блока кнопок. Координаты подсказывают район
  запросу Яндекса и Apple и помогают Apple, если идентификатор не узнан;
- по полям `maps` сборка сама строит ссылки (см.
  [4.5](#45-ссылки-на-карты)). Кладут идентификатор или запрос, а не ссылку.

Поля `maps` (все необязательные); у каждой карты берётся первое заданное по
порядку «идентификатор → запрос»:

| Поле | Карта | Значение | Где взять |
|---|---|---|---|
| `googlePlaceId` | Google | Place ID: только `A–Z`, `a–z`, `0–9`, `_` и `-` | страница Place ID Finder в документации Google Maps Platform |
| `googleQuery` | Google | текстовый запрос | — |
| `yandexOrgId` | Яндекс | номер организации: только цифры | число после `/org/<название>/` в адресе карточки организации на Яндекс Картах |
| `yandexGeoId` | Яндекс | номер геообъекта (здание, вход — то, у чего нет карточки организации): только цифры | число после `/geo/<название>/` в адресе карточки объекта на Яндекс Картах |
| `yandexQuery` | Яндекс | текстовый запрос | — |
| `applePlaceId` | Apple | Place ID: только `A–Z`, `a–z` и `0–9` | Place ID Lookup в документации Apple Maps; параметр `place-id` в ссылке «Поделиться» из Apple Карт, если он там есть |
| `appleQuery` | Apple | текстовый запрос | — |

- **текстовый запрос** — то, что гость набрал бы в поиске этой карты, например
  `"Гостевой вход, Энск"`: название и город. Он нужен, когда у места нет своего
  идентификатора, например у отдельного входа в большое здание. Одна строка,
  от 1 до 200 символов, без управляющих символов; пустая строка или строка из
  пробелов — ошибка (поле тогда просто не пишут). У каждой карты свой запрос:
  в разных картах одно и то же место может называться по-разному;
- `yandexOrgId` и `yandexGeoId` вместе — ошибка («set either 'yandexOrgId' or
  'yandexGeoId'»): одно место — один вид идентификатора;
- общего поля `query` нет — сборка подскажет разнести запрос по картам.

```json
"maps": { "googleQuery": "Гостевой вход, Энск", "yandexGeoId": "1234567890",
          "applePlaceId": "IEXAMPLE0000001" }
```

#### Программы (`schedules.<id>`)

Массив пунктов `{ "time": …, "title": …, "text": … }`: `title` обязателен (одна
строка), `time` — одна строка, `text` — многострочный. В `title` и `text`
работают формы и подстановки ([3.6](#36-тексты-формы-обращения-и-подстановки)),
`time` — обычная строка. Пустая программа — предупреждение, она не выводится.

#### Медиа (`media.<id>`)

| Поле | Тип | Правила |
|---|---|---|
| `type` | `"image"` / `"video"` | обязателен |
| `file` | имя файла | обязателен; картинка — `.png`, `.jpg`, `.jpeg`, `.webp`, `.avif`, `.gif`, `.svg`; видео — только `.mp4` |
| `poster` | имя файла-картинки | у видео обязателен, у картинки запрещён |
| `thumb` | имя файла-картинки | картинка для плитки; по умолчанию постер, у фото — сам файл |
| `width`, `height` | целые > 0 | оба или ни одного |
| `alt` | строка | одна строка: описание для экранного диктора; без него — предупреждение и подпись «Фотография» / «Видео» |

- **размер** нужен, чтобы место под плитку резервировалось до загрузки и окно
  просмотра знало пропорцию кадра. Без `width`/`height` сборка читает размер из
  заголовка картинки (PNG, JPEG, WebP; у видео — постера) или из самого `.mp4`;
  если не удалось — предупреждение, и одиночная плитка получает пропорцию
  16:9 из токена;
- у видео сборка сама читает **длительность** (показывается на плитке) и
  проверяет файл: без `+faststart`, не H.264, HDR, нечитаемая длительность,
  постер другой пропорции, чем `width`/`height` (больше чем на 1 %), —
  предупреждения; не тот тип содержимого, чем говорит расширение, — ошибка;
- **подписи под плиткой нет**: у плитки фиксированная пропорция, текст под ней
  не помещается, поэтому поле `caption` — ошибка с подсказкой; описывает
  картинку `alt`;
- элемент реестра, который не показан ни на одной странице, — предупреждение,
  его файлы не публикуются и даже не читаются.

Требования к видеофайлу и его подготовка — раздел [8](#8-видео).

### 3.3. Правила токенов

Токен придумывают сами или получают командой `token`; он может быть читаемым
(`quokka`, `heron-4tx9`):

- допустимые символы: `A–Z`, `a–z`, `0–9`, `_`, `-`;
- длина — от 5 до 200 символов: токен становится именем каталога;
- токен из одних шестнадцатеричных цифр и дефисов (вроде UUID) проверяется
  так же, как любой другой, — особых правил для него нет;
- уникальность **без учёта регистра** — каталоги `i/ABC…` и `i/abc…` совпадут на
  файловой системе, не различающей регистр;
- после рассылки токены не меняют: старые ссылки перестанут работать.

Новый токен: `python3 build.py token` (случайный) или
`python3 build.py token --prefix <имя>` (читаемый со случайным хвостом,
[2.3](#23-token--новый-токен-приглашения)).

**Токен — единственная защита страницы гостя.** Кто знает или угадал адрес
`/i/<token>/`, видит страницу целиком: обращение, приписки (например, про
аллергию), события и места, скрытые от других гостей, календарные файлы.
Короткий читаемый токен из имени или прозвища подбирается перебором по словарю:
имена, клички, сочетания вроде `*_queen`, `cat_*`. Поэтому:

- делайте токен **не короче 12 символов** — сборка считает более короткие и
  сообщает их число строкой `tokens: …` ([2.11](#211-коды-возврата-и-журнал));
- не делайте токен из одного имени — добавьте то, что знаете только вы и гость;
- если нужен читаемый токен, добавьте короткий случайный хвост:
  `token --prefix heron` → `heron-4tx9`; читаемость остаётся, а перебор по
  словарю становится дороже примерно в миллион раз;
- не пишите в приписки чувствительного — здоровья, адресов, телефонов: при
  угаданном токене это прочтёт посторонний.

От перебора защищают только длина и непредсказуемость токена. Замедлить
перебор может лишь ограничение частоты запросов к `/i/*` на хостинге, если
тариф его позволяет. Остальные меры сайта от перебора не спасают:
`noindex` и `robots.txt` (раздел [9](#9-заголовки-приватность-индексация))
только не пускают страницы в поисковики, а одинаковая заглушка на корень и на
любой неверный путь только не подсказывает, насколько близко угадан адрес.
Ни то, ни другое не замедляет и не останавливает подбор.

### 3.4. Каталог медиа и имена файлов

`mediaDir` — случайное имя каталога, в который сборка кладёт медиа: файлы
публикуются по пути `/assets/<mediaDir>/…`, поэтому по адресу картинки нельзя
угадать ни структуру ссылок, ни что-либо о событии.

- длина 16–200 символов, символы `A–Z`, `a–z`, `0–9`, `_`, `-`;
- имя не должно совпадать (без учёта регистра) с чем-то, что уже есть в
  `assets/` (`fonts`, …) — сборка это проверяет.

**Имена в сборке — хэши содержимого.** Файл публикуется не под своим именем, а
как `/assets/<mediaDir>/<первые 16 знаков sha256 содержимого>.<расширение>`,
например `…/6606d330914742c8.png`. Имя из данных в сборку не попадает вовсе, и
файл секции, показанной одному гостю, нельзя найти перебором имён. Файлы с
одинаковым содержимым и расширением публикуются один раз; сборка остаётся
воспроизводимой. Публикуются **только файлы элементов, показанных хотя бы на
одной странице**: остальные сборка не читает и не копирует (и предупреждает о
неиспользуемом элементе реестра).

**Календарные файлы** лежат там же, по одному на событие, которое видно хотя бы
одному гостю: `/assets/<mediaDir>/<16 знаков>.ics`. Имя — хэш содержимого с
ключом из **токенов всех приглашений**. Чтобы вычислить имя файла скрытого
события, нужно знать все токены, поэтому файл защищён так же, как страницы
гостей. Подробнее — в разделе [5](#5-что-получается-в-dist-и-что-проверяется).

Имена медиафайлов в данных:

- **простое имя файла** внутри каталога медиа: без `/`, `\` и `..`, не начинается
  с точки, без управляющих символов;
- **двоеточие запрещено** — такое имя нельзя создать на части файловых систем;
- **регистр учитывается**: `Venue-1.png` и `venue-1.png` — разные файлы (если
  файл не найден, но отличается только регистром, сборка скажет об этом);
- допустимые расширения: картинки — `.png`, `.jpg`, `.jpeg`, `.webp`, `.avif`,
  `.gif`, `.svg`; видео — только `.mp4`;
- символические ссылки вместо файлов не принимаются, размер каждого файла — не
  больше 25 MiB.

Сообщения о файлах называют поле (`field 'media.walk.file': the file is missing
from media`), а не имя файла: имя — тоже данные. Зарезервированных имён нет:
календарные файлы получают имена-хэши с расширением `.ics`, которого у медиа не
бывает (совпадение имён сборка всё равно проверяет и считает ошибкой).

**Каталога медиа может не быть вовсе.** Если страницы не показывают ни одного
медиа (например, места не объявлены и реестра `media` нет), путь `--media`
может указывать на несуществующий каталог — сборка пройдёт, а в
`assets/<mediaDir>/` в `dist/` окажутся одни календарные файлы. Так собирается
второй пример:

```
python3 build.py build --data examples/data-venue-pending --media examples/media-none
```

### 3.5. Своя иконка и своя картинка предпросмотра

**Картинка превью ссылки — титульник.** Сборка рисует её сама, при каждой
сборке: та же обложка, что наверху страницы (`template.html`,
`fragments/sections/cover.html`, `app.css`, фото `background` под вуалью с
`backgroundFocus`, имена пары, разделитель, дата), в headless Chrome, одной
командой `build`. Отличия от страницы гостя — данных гостя в общей картинке
быть не может:

- дата — **основного события** (`mainEvent`);
- `eyebrow` обложки выводится, только если он не зависит от гостя: строка без
  форм и без `{greeting}` (общие тексты в общей форме `all` и подстановки
  сайта допустимы); иначе он опускается, а `validate` пишет об этом одну
  строку;
- панели обложки нет, скрипты страницы не выполняются.

Формат — **JPEG 1200×630**, вес — **не больше 300 KB** (официальный предел
WhatsApp — 600 KB, но на практике он теряет картинку уже около 300 KB):
качество подбирается вниз от 85 до 60, не уложились — предупреждение, картинка
публикуется всё равно. **Безопасная зона**: имена и дата — в центральном
квадрате 630×630 (маленькие превью обрезают картинку по центру до квадрата);
раскладку кадра задаёт `assets/preview.css`, а если обложка с длинными
именами не помещается в «телефонное» окно 600×315 (масштаб ×2), сборка берёт
окно 800×420 (×1,5), затем 1200×630. Картинка публикуется как остальные медиа:
`assets/<mediaDir>/<sha256[:16]>.jpg`, одна на сайт; по угадываемому адресу
`/assets/og.*` картинки с данными нет никогда.

**Сайт без обложки** (без секции `type: "cover"`) получает нейтральную
картинку из токенов — `assets/og.png`, как раньше; так же — с флагом
`--no-link-preview-image` (`LINK_PREVIEW_IMAGE=off`). `og.png` пишется, только
когда на неё ссылаются страницы.

**Своя картинка** — явная замена титульника для тех, кто хочет нарисовать
превью сам: файл `og.png` или `og.jpg` в **каталоге медиа**. Он тоже
публикуется в `assets/<mediaDir>/` под хэшем содержимого (а не в `/assets/`),
Chrome тогда не нужен. Пропорции, далёкие от 1200×630 (≈1,91:1), вызывают
предупреждение: сервисы картинку обрежут.

**Своя иконка** — `favicon.svg`, `favicon.png` или `favicon.ico` в каталоге
медиа (побеждает первое из существующих); она публикуется как
`assets/favicon.<ext>`, по умолчанию иконка рисуется из токенов.

В `site.json` эти файлы упоминать не надо. К ним применяются те же правила,
что и к остальным медиа. Файл, который только похож на них (другой регистр,
другое расширение, проигравшее имя), не публикуется — сборка предупреждает об
этом, чтобы никто не ждал картинку, которая никогда не появится.

Имена `favicon.*` и `og.*` внутри `assets/` заняты сборкой: файл с таким именем
в `assets/` остановит сборку с подсказкой положить его в каталог медиа.

### 3.6. Тексты: формы обращения и подстановки

**Где что можно:**

| Где | Формы «ты/вы» | Подстановки |
|---|---|---|
| `title` и `eyebrow` секции, `text` виджета «Текст» | да | да, и `{text:<id>}` |
| приписки гостя (`note`) | нет | да, и `{text:<id>}` |
| общие тексты `texts.<id>` | да, плюс общая форма `all` | да, и `{text:<id>}` |
| `linkPreview.description` | нет (тексты — в общей форме `all`) | только уровня сайта (без `{greeting}`; `{event…}` — основного события), и `{text:<id>}` |
| `description` события и места, `title` и `text` пункта программы | да | да, и `{text:<id>}` |
| `title` события, `name` и `address` места, `greeting`, `coupleNames`, `rsvpDeadline`, `alt` медиа | нет | нет |

Последняя строка — то, что уходит в **общие файлы**: название события и его
место попадают в календарный файл, одинаковый у всех, кто видит событие, а
`greeting`, `coupleNames` и `rsvpDeadline` сами служат значениями подстановок.
Данных конкретного гостя в них быть не должно.

Описания событий и мест и тексты программы календарный файл не покидают: их
видно только на странице гостя, поэтому там формы и подстановки работают, как
в тексте секции. `{eventDate}`, `{eventTime}`, `{eventTitle}` и `{eventPlace}`
везде — **первостепенного события гостя**, а не того события, чьё описание
разворачивается.

**Формы.** Текст — либо строка, одна на всех, либо объект с обоими вариантами:

```json
"text": { "ty": "Ждём тебя {eventDate} в {eventTime}.",
          "vy": "Ждём вас {eventDate} в {eventTime}." }
```

Гость получает вариант по своему полю `form`. Объект без одного из вариантов —
ошибка.

**Подстановки** — имя в фигурных скобках:

| Подстановка | Значение |
|---|---|
| `{coupleNames}` | `coupleNames` |
| `{greeting}` | обращение гостя |
| `{rsvpDeadline}` | `rsvpDeadline` (если поля нет — ошибка) |
| `{eventTitle}` | название первостепенного события гостя |
| `{eventDate}` | его дата: «15 июня 2030» |
| `{eventTime}` | его время: «16:00» |
| `{eventPlace}` | название его места; если место не объявлено — пустая строка и предупреждение |

Неизвестное имя, незакрытая скобка и пустые скобки — ошибки (с номером символа;
сам текст в сообщение не попадает). `{{` и `}}` — буквальные фигурные скобки.
Подставленные значения не разбираются повторно: скобки в обращении гостя
остаются текстом.

**Общие тексты — `texts` и `{text:<id>}`.** Текст, который нужен в нескольких
местах (например, основной текст приглашения и описание превью ссылки), пишут
один раз в реестре `texts` и вставляют по id:

```json
"texts": {
  "announce": "Мы, {coupleNames}, женимся!",
  "invite": { "ty":  "Ждём тебя {eventDate} в {eventTime}.",
              "vy":  "Ждём вас {eventDate} в {eventTime}.",
              "all": "Ждём вас {eventDate} в {eventTime}." } }
```

```json
{ "type": "text", "variant": "lead", "text": "{text:announce}" }
```

- id — по правилу [3.7](#37-id--не-место-для-имён); значение — строка (одна на
  всех) или объект с `ty` и `vy` и необязательной **общей формой `all`**;
  многострочные тексты и подстановки — как у текста виджета;
- **общая форма `all`** — вариант для мест, где гостя нет (описание превью
  ссылки, [3.8](#38-рецепты)). В ней нельзя `{greeting}` (в том числе через
  вложенные тексты), а `{event…}` берут **основное** событие (`mainEvent`).
  На страницах гостей `all` не используется. Ключ `all` допустим только в
  `texts`: в `text` виджета, `title`, `eyebrow` — ошибка. Строка без форм
  сама служит общей формой, если в ней нет `{greeting}`;
- `{text:x}` работает там же, где подстановки: `title`, `eyebrow`, `text`
  виджета, приписки гостя, `linkPreview.description`, `description` события и
  места, `title` и `text` пункта программы. В `title` события, `name` и
  `address` места, `greeting`, `coupleNames`, `rsvpDeadline` и `alt` — нет
  (там это обычный текст).

**Как разворачивается:**

1. у поля выбирается вариант по форме гостя (`ty`/`vy`);
2. каждая `{text:<id>}` заменяется вариантом этого текста **для той же формы**
   (строка подходит любой форме);
3. тексты могут ссылаться друг на друга — разворачивается рекурсивно; **цикл**
   (`a → a`, `a → b → a`) — ошибка с цепочкой id; вложенность — не больше 8;
4. после этого одним проходом — подстановки (`{coupleNames}`, `{eventDate}` …) с
   `{event…}` первостепенного события гостя. Подставленные значения не
   разбираются: `{text:…}` в обращении гостя остаётся текстом.

Ошибки: неизвестный id (с подсказкой и списком известных), `{text:}` и id не
по правилу (с номером символа), цикл и вложенность, многострочный текст в
однострочном поле (`title`, `eyebrow`). Текст из `texts`, который не
показан ни на одной странице и не входит в описание превью, — предупреждение.
`{{text:x}}` — буквальный текст.

**Многострочные тексты** (текст виджета, описания, приписки, пункты программы):
пустая строка — новый абзац, одиночный перенос — перенос строки. Поля, которые
попадают в заголовки и подписи (`title`, `eyebrow`, `greeting`, `coupleNames`,
названия событий и мест, адрес, `time` и `title` пунктов программы, `alt`),
должны быть **однострочными** — это проверяет валидация.

Служебные подписи интерфейса («Добавить в календарь», «Программа», подписи
таймера, «Подробности появятся на этой странице позже.») живут во фрагментах
шаблона, а не в данных.

### 3.7. Id — не место для имён

Id секций, виджетов, событий, мест, программ и медиа: 1–32 символа, строчные
латинские буквы, цифры и одиночные дефисы, начинается с буквы (`dinner`,
`hotel-booked`, `venue-1`). Два дефиса подряд запрещены: ими сборка склеивает
части DOM-id ([4.7](#47-фрагменты-секций-и-виджетов)).

Id **видны**: в атрибутах `id` разметки и в сообщениях сборки. Поэтому в id не пишут ни имён
гостей, ни подробностей события: `plus-one`, а не `plus-one-ivan`; `hotel`, а не
название гостиницы. Имя гостя в ключах `invitations.json` сборка всё равно в
сообщения не выпустит ([3.1](#31-invitationsjson--массив-приглашений)), но id
из `site.json` печатаются как есть.

### 3.8. Рецепты

Все рецепты — правка данных, код не меняется. Примеры из `examples/data/`
устроены именно так.

**Секция только для иногородних.** Секция в `site.json` скрыта по умолчанию,
иногородним гостям она включена:

```json
{ "id": "travel", "title": "Гостям из других городов", "visible": false,
  "widgets": [ { "type": "text", "text": "От вокзала ходит трансфер." },
               { "type": "location", "location": "hotel", "variant": "compact" } ] }
```

```json
{ "token": "…", "greeting": "Дорогая Ева!", "form": "ty",
  "sections": { "travel": { "visible": true } } }
```

**«+1» — абзац в тексте приглашения.** Текст «+1» — не отдельная секция, а
часть приглашения: текстовый виджет с `id`, скрытый по умолчанию, между
основным текстом и «Ждём…». Три соседних виджета `lead` читаются как один
текст — между ними обычный шаг абзаца, а не шаг между виджетами:

```json
{ "id": "invite", "title": "{greeting}", "align": "center",
  "widgets": [
    { "type": "text", "variant": "lead", "text": "{text:announce}" },
    { "id": "plus-one", "type": "text", "variant": "lead", "visible": false,
      "text": { "ty": "Ты можешь прийти со спутником или спутницей.\nПожалуйста, сообщи нам заранее имя своего гостя.",
                "vy": "Вы можете прийти со спутником или спутницей.\nПожалуйста, сообщите нам заранее имя вашего гостя." } },
    { "type": "text", "variant": "lead", "text": "{text:invite}" } ] }
```

Основной текст — два общих текста из `texts` (следующий рецепт).

Тому, кто может прийти со спутником, виджет включается:

```json
{ "token": "…", "greeting": "Дорогая Кэрол!", "form": "ty",
  "sections": { "invite": { "widgets": { "plus-one": { "visible": true } } } } }
```

У остальных этого абзаца нет ни на странице, ни в её HTML. Так же делается
любой текст «только для некоторых гостей» внутри секции: виджет получает `id`
и `"visible": false`, а гостю включается через `"widgets"` своей секции — как
«Для вас забронирован номер» (`hotel-booked`) в секции `travel` примеров.

**Общие тексты: объявление и приглашение.** Основной текст приглашения
состоит из двух частей — объявления («Мы, <имена>, женимся!») и приглашения
(«Ждём вас …»). Обе — в `texts` ([3.6](#36-тексты-формы-обращения-и-подстановки)):
на странице гость получает свою форму, описание превью ссылки собирается из
тех же текстов в общей форме `all`:

```json
"texts": {
  "announce": "Мы, {coupleNames}, женимся!",
  "invite": { "ty":  "Ждём тебя {eventDate} в {eventTime}.\nНам очень хочется разделить этот день с тобой.",
              "vy":  "Ждём вас {eventDate} в {eventTime}.\nНам очень хочется разделить этот день с вами.",
              "all": "Ждём вас {eventDate} в {eventTime}." } }
```

**Превью ссылки.** Описание в карточке ссылки собирается из тех же общих
текстов в общей форме `all`; `{event…}` берут **основное** событие, поэтому
описание одинаково у всех гостей:

```json
"linkPreview": { "description": "{text:announce} {text:invite}" }
```

→ «Мы, Алиса и Боб, женимся! Ждём вас 15 июня 2030 в 16:00.» Переносы строк
сводятся к пробелу. Текст с формами без `all`, `{greeting}` (прямо или через
текст) и объект форм в самом поле — ошибки. Главное — в первые 80 символов
(столько показывает WhatsApp); длиннее 200 — предупреждение. `//` и `http` в
описании не пройдут проверку результата (внешний адрес в `<meta>`). Нет поля —
нет и описания. Заголовок карточки — «Приглашение · <имена пары>», он в
шаблоне и своего поля не имеет.

**Приписка гостю.** К секции — карточка в конце секции; к событию — в
карточке события:

```json
"sections": { "personal": { "note": "Помнишь, как мы познакомились?\n\nЖдём!" } },
"events": { "dinner": { "note": "Напиши нам про аллергию — подберём меню." } }
```

Для личной приписки удобна секция без виджетов (`"widgets": []`): у кого
приписки нет, у того её и не видно.

**Событие только для приглашённых.** В реестре событие скрыто, нужным гостям
оно включено; остальные видят все прочие события, а скрытого нет на их
странице — ни карточки, ни даты, ни ссылки на его календарный файл:

```json
"brunch": { "title": "Второй день", "location": "terrace",
            "start": "2030-06-16T12:00:00+03:00",
            "end": "2030-06-16T15:00:00+03:00", "visible": false }
```

```json
"events": { "brunch": { "visible": true } }
```

**Первостепенное событие.** Кого зовут только на регистрацию, у того
первостепенным должно быть оно — обложка, дата, таймер и `{eventDate}` возьмут
его время:

```json
{ "token": "…", "greeting": "Дорогие Пегги и Виктор!", "form": "vy",
  "primaryEvent": "ceremony" }
```

Если гостю скрыто основное событие (`mainEvent`), `primaryEvent` обязателен.

**Свой текст с формами «ты/вы».** Любая обычная секция с виджетом «Текст»:

```json
{ "id": "rsvp", "title": "Подтверждение", "align": "center",
  "widgets": [
    { "type": "text",
      "text": { "ty": "Пожалуйста, ответь нам до {rsvpDeadline}.",
                "vy": "Пожалуйста, ответьте нам до {rsvpDeadline}." } },
    { "type": "text", "variant": "signature", "text": "{coupleNames}" } ] }
```

Заголовок секции тоже может быть текстом с формами или подстановкой:
`"title": "{greeting}"`.

**Добавить фото или видео.** Файл кладут в каталог медиа, описывают в реестре
и показывают виджетом «Медиа» или в `photos` места:

```json
"media": {
  "story-1": { "type": "image", "file": "story-1.jpg", "alt": "Первая встреча" },
  "walk": { "type": "video", "file": "walk.mp4", "poster": "walk-poster.jpg",
            "width": 1280, "height": 720, "alt": "Прогулка по усадьбе" } }
```

```json
{ "id": "story", "title": "Наша история",
  "widgets": [ { "type": "media", "items": ["story-1", "walk"] } ] }
```

Видео — только `.mp4` (H.264 + AAC, `+faststart`), постер обязателен и той же
пропорции; как подготовить файл — раздел [8](#8-видео). Одиночный ролик
крупно — `"layout": "single"`.

**Фото на обложке.** Картинку кладут в каталог медиа, описывают в реестре
(`alt` не нужен: фон декоративный) и указывают у обложки:

```json
{ "id": "cover", "type": "cover", "background": "cover", "backgroundFocus": "center" }
```

```json
"media": { "cover": { "type": "image", "file": "cover.jpg" } }
```

Фото заполняет обложку при любой пропорции экрана: лишнее обрезается, полос
нет. Поверх фото — полупрозрачная вуаль цвета обложки, весь текст обложки на
фото — основным цветом, поэтому он читается на любом кадре, даже на почти
чёрном. Фото видно приглушённым — так и задумано. Кадр один на все экраны:

- **файл** — длинная сторона 2000–2400 px, JPEG с качеством около 70 или WebP,
  **не больше ~400 KB** (под вуалью артефакты сжатия не видны). Сборка файл не
  уменьшает; больше 1 MiB — предупреждение: фото грузится первым, до всего
  остального;
- **фокус** (`backgroundFocus`) — какая часть кадра остаётся видна, когда экран
  его обрезает. На телефоне в портретной ориентации ландшафтный кадр
  обрезается слева и справа, на широком экране — сверху и снизу. По умолчанию
  `center`; лица у верхнего края — `top`, пара слева — `left`, углы —
  `top-left`, `bottom-right` и т. д. Проверить — открыть страницу на узком и на
  широком окне;
- печатается обложка без фото.

Без `background` обложка — как раньше, однотонная (пример без площадок).

**Кнопки карт.** Кнопка появляется только у той карты, для которой место
задано в `maps`; одних координат мало. Место с карточкой организации — по
идентификаторам, отдельный вход в большое здание — запросом с городом:

```json
"manor": { "name": "Усадьба «Образец»", "geo": { "lat": 12.345678, "lng": 23.456789 },
           "maps": { "googlePlaceId": "EXAMPLE-not-a-real-place-id",
                     "yandexOrgId": "1000000001", "applePlaceId": "IEXAMPLE0000001" } },
"registry": { "name": "Дворец бракосочетания Энска",
              "maps": { "googleQuery": "Гостевой вход, Дворец бракосочетания, Энск",
                        "yandexGeoId": "1234567890",
                        "appleQuery": "Гостевой вход, Дворец бракосочетания, Энск" } }
```

Нужна только одна карта — задают только её поля. Место без `maps` (как
`hotel` в примерах) выводится без кнопок карт. Раньше кнопки строились по одним
координатам; теперь для каждой нужной карты добавьте идентификатор или запрос
(форматы — в разделе «Места» выше и в [4.5](#45-ссылки-на-карты)).

## 4. Шаблон

`template.html` — каркас страницы: `<head>` и `<main>`, в который
`<!-- include:partials/sections -->` выводит секции; вся разметка секций и
виджетов — во фрагментах ([4.7](#47-фрагменты-секций-и-виджетов)). Каркас и
фрагменты — обычный HTML, который можно открыть в браузере и посмотреть
разметку. Данные подставляются тремя видами конструкций — значения (`{{…}}`),
условия и списки — и ничем больше. Директивы `include` и `with` значений из
данных не выводят: `include` вставляет разметку фрагмента, `with` меняет
текущий элемент.

`<head>` страницы приглашения — заголовок и теги превью ссылки, одинаковые у
всех гостей:

```html
<title>Приглашение · Алиса и Боб</title>
<meta name="description" content="Мы, Алиса и Боб, женимся! Ждём вас 15 июня 2030 в 16:00.">
<meta property="og:title" content="Приглашение · Алиса и Боб">
<meta property="og:description" content="(то же описание)">
<meta property="og:type" content="website">
<meta property="og:locale" content="ru_RU">
<meta property="og:site_name" content="Приглашения">   <!-- только с SITE_NAME -->
<meta property="og:image" content="/assets/…">          <!-- всегда путь от корня -->
<meta property="og:image:type" content="image/jpeg">
<meta property="og:image:width" content="1200">
<meta property="og:image:height" content="630">
<meta property="og:image:alt" content="Приглашение · Алиса и Боб">
<meta name="twitter:card" content="summary_large_image">
```

«Приглашение · » — служебная подпись, живёт в шаблоне; описание
(`linkDescription`) и название сайта (`siteName`) выводятся, только если
заданы. `og:url` нет.

### 4.1. Синтаксис

| Конструкция | Что делает |
|---|---|
| `{{field}}` | значение поля |
| `{{a.b}}` | вложенное поле (`{{primaryEvent.title}}`) |
| `{{.field}}` | поле текущего элемента внутри `each` или `with` |
| `{{.}}` | сам текущий элемент внутри `each` — только для массива простых значений |
| `<!-- if:flag --> … <!-- endif -->` | блок, если значение «истинно» |
| `<!-- if:!flag --> … <!-- endif -->` | блок, если значение «ложно» |
| `<!-- each:list --> … <!-- endeach -->` | повтор по массиву |
| `<!-- with:obj --> … <!-- endwith -->` | объект `obj` становится текущим элементом `.`; `null`, `false` и `{}` пропускают блок |
| `<!-- include:dir/name -->` | вставляет фрагмент `fragments/dir/name.html`; он видит те же поля страницы и тот же текущий элемент `.`, что и место включения |
| `<!-- include:dir/{{.type}} -->` | **выбор по типу**: вставляет `fragments/dir/<значение .type>.html`; только внутри `each` или `with` того же файла |

Правила:

- директивы пишутся строчными буквами; имя поля — латиница, цифры и `_`;
- «истинно» — `true`, непустая строка, непустой массив, непустой объект,
  число ≠ 0. «Ложно» — отсутствующее поле, `null`, `false`, `""`, `[]`, `{}`,
  `0`;
- внутри `each` и `with` доступны и поля элемента (`{{.time}}`), и поля
  страницы (`{{coupleNames}}`);
- `with` над отсутствующим полем или над значением, которое не объект (строка,
  число, массив, `true`), — ошибка сборки; `with:.` тоже ошибка;
- `{{.}}` годится только для массива строк или чисел: вставить объект или
  вложенный массив целиком нельзя — это ошибка сборки с подсказкой. Все массивы
  дерева страницы ([4.4](#44-дерево-страницы)) состоят из объектов, поэтому во
  фрагментах используется `{{.field}}`;
- блоки вкладываются; незакрытый или перепутанный блок — ошибка сборки с номером
  строки;
- обращение к несуществующему полю — ошибка сборки (опечатка не превратится в
  пустое место);
- комментарий, не похожий на директиву, остаётся обычным HTML-комментарием и
  **удаляется из готовой страницы**, так что заметки в шаблоне никуда не
  попадают.

**Фрагменты.** Общие куски разметки и разметку, которую выбирают данные, выносят
в каталог `fragments/` рядом с `template.html`:

- имя фрагмента — путь к файлу без `.html`: части из `a-z`, `0-9` и `-`,
  каждая начинается с буквы и не длиннее 40 символов, разделитель — `/`
  (`widgets/text` → `fragments/widgets/text.html`). В каталоге — только файлы
  `.html` и подкаталоги: символическая ссылка или другое расширение — ошибка
  сборки, файлы и каталоги с точкой в начале имени пропускаются. Если каталога
  нет, фрагментов нет;
- все фрагменты читаются и проверяются один раз, до сборки страниц; во время
  рендера файлы не читаются. Ещё до рендера сборка останавливается, если во
  фрагменте синтаксическая ошибка (сообщение называет файл и строку), если
  включается несуществующий фрагмент, если фрагменты включают друг друга по
  кругу, если выбор по типу стоит вне `each`/`with` или ведёт в пустой или
  отсутствующий каталог. `each`/`with` для выбора по типу должен стоять в том
  же файле: выбор на верхнем уровне фрагмента — ошибка, даже если сам фрагмент
  включён внутри `each`;
- `{{.field}}` во фрагменте вне его собственных `each`/`with` — поле элемента
  места включения. Такой фрагмент, а также фрагмент, который включает его вне
  своих `each`/`with`, можно включить в `template.html` только внутри `each` или
  `with` — иначе ошибка сборки;
- **выбор по типу**: каталог задаёт шаблон, данные выбирают только имя файла в
  нём. Значение поля — строка из одной части имени (без `/`), и это имя
  фрагмента, который лежит прямо в этом каталоге. Иначе — ошибка сборки: «the
  value of '.type' is not a fragment name» или «no fragment in
  fragments/widgets/ for the value of '.type' (known: …)». Само значение в
  сообщение не попадает, известные имена берутся из файлов кода. Выбирать можно
  только по полю текущего элемента, в том числе вложенному
  (`{{.media.type}}`); фрагменту достаётся сам элемент;
- ошибка при рендере фрагмента (нет поля, неизвестный тип) называет файл
  фрагмента, строку и цепочку включений:

  ```
  fragments/widgets/text.html line 5: field '.txt' not found (included from fragments/sections/custom.html line 8 <- template.html line 33)
  ```

- фрагменты вкладываются не глубже 12 уровней — дальше ошибка сборки (так
  останавливается рекурсия через данные);
- блок (`if`, `each`, `with`) открывается и закрывается в одном файле;
- экранирование, переносы строк, «ложные» значения, ошибка на несуществующее
  поле и удаление комментариев работают во фрагментах так же, как в
  `template.html`;
- доступа к полям внешнего элемента, сравнений, параметров включения и `else`
  нет: нужное сборка кладёт в сам элемент, вместо параметров —
  `<!-- with:… --><!-- include:… --><!-- endwith -->`, вместо `else` — пара
  `if:x` / `if:!x`.

### 4.2. Как подставляется текст

Значение сначала экранируется (`<`, `>`, `&`, кавычки, а также `{` и `}`), потом
переносы строк превращаются в разметку:

- `\r\n` и `\r` приводятся к `\n`;
- пустая строка (два и больше переноса подряд) → `</p><p>`;
- одиночный перенос → `<br>`;
- пустые строки в начале и в конце отбрасываются.

Отсюда правило: **многострочное поле должно быть единственным содержимым своего
`<p>…</p>`**:

```html
<p>{{.note}}</p>                        <!-- правильно -->
<p>Пожелание: {{.note}} — спасибо!</p>  <!-- неправильно: абзацы разорвут разметку -->
```

Поля, которые попадают в заголовки, атрибуты и подписи (заголовки секций,
`greeting`, `coupleNames`, `rsvpDeadline`, названия событий и мест, адреса,
`time` и `title` пунктов программы, `alt`), проверяются на однострочность ещё
на этапе проверки данных ([3.6](#36-тексты-формы-обращения-и-подстановки));
строки дат пишет сама сборка.

### 4.3. Чего нельзя в шаблоне

Сборка **отвергает** (проверка идёт не по шаблону, а по готовым страницам, см.
раздел 5, поэтому обойти её подстановкой данных нельзя):

- **литеральные `{{` и `}}`** вне подстановки: они означают незаполненный
  плейсхолдер (в данных `{{` безопасно — оно экранируется);
- **`<style>`** — стили только файлами в `/assets/`;
- **inline-скрипты и обработчики** (`onclick=…`) — скрипты только файлами;
- **`<meta http-equiv="refresh">`**, `<iframe>`, `<object>`, `<embed>`,
  `<frame>`, `<base>`;
- **CDATA (`<![…`) и инструкции обработки (`<?…`)**;
- **любые HTML-комментарии в результате** — они удаляются при рендере, а
  уцелевший комментарий (например, из-за незакрытого `-->`) останавливает
  сборку;
- **текст, который разборщик видит именно как текст, а браузер может прочитать
  как разметку** — содержимое `<title>` и `<textarea>` внутри `<svg>`,
  «хвост» незакрытого комментария: там `<` перед буквой, `/`, `!` или `?`
  запрещён;
- относительные пути к ресурсам: только абсолютные от корня (`/assets/…`).

**Зарезервированные слова.** Комментарий, который начинается с `if:`, `each:`,
`with:`, `include:`, `endif`, `endeach` или `endwith` (в любом регистре),
сборка читает как директиву, и неверно записанная директива — ошибка сборки.
Обычные заметки в шаблоне и во фрагментах так не начинают. Уцелевшая в готовой
странице директива останавливает сборку (раздел 5).

**Заглушка** (`stub.html`) фрагменты не включает: `include` в ней — ошибка
сборки (см. [4.6](#46-заглушка)).

**Правило для автора шаблона, которое сборка проверить не может.** Литеральный
`<` в обычном тексте (`<y z>`, `</b c>`) разборщик читает как тег — для него это
разметка, а не текст, поэтому такая запись проходит проверки и попадает на
страницу неизвестным элементом. Поэтому знак «меньше» в тексте шаблона всегда
пишут как `&lt;`. В данных этого делать не нужно: значения экранируются при
подстановке.

### 4.4. Дерево страницы

Шаблон и фрагменты получают не данные как они есть, а **дерево страницы**
гостя (`tools/_page.py`). Сборка строит его для каждого приглашения:

- скрытого у гостя в дереве нет вовсе — ни секций, ни виджетов, ни событий, ни
  чужих приписок, ни ссылок на календарные файлы скрытых событий;
- тексты готовые: форма обращения выбрана, подстановки выполнены;
- строки дат, адреса файлов (с именами-хэшами), ссылки на карты, размеры и
  длительность медиа, DOM-id посчитаны заранее;
- **каждое поле существует всегда**: пустая строка, `[]`, `false` или `null`
  вместо отсутствующего значения, поэтому `if:` и `{{…}}` никогда не
  спотыкаются об отсутствие поля. Фрагмент читает только поля из этого
  перечня — тест проверяет это, отдавая фрагментам дерево, в котором чтение
  любого другого поля роняет рендер.

**Корень:**

| Поле | Значение |
|---|---|
| `greeting`, `form`, `ty`, `vy` | обращение гостя, форма (`ty` / `vy`) и два признака формы |
| `coupleNames`, `rsvpDeadline` | из `site.json` (`rsvpDeadline` — `""`, если не задан) |
| `mediaPath` | `/assets/<mediaDir>` |
| `faviconPath`, `faviconType` | путь и MIME-тип иконки |
| `ogImage`, `ogImageType`, `ogImageWidth`, `ogImageHeight` | картинка предпросмотра |
| `themeColor` | цвет интерфейса браузера, `#rrggbb` из токена `--color-cover-veil` ([6.7](#67-иконка-картинка-предпросмотра-и-цвет-интерфейса-браузера)) |
| `linkDescription` | описание превью ссылки: `linkPreview.description` в общей форме, пробелы схлопнуты; одинаково у всех гостей; `""` без поля |
| `siteName` | название сайта для `og:site_name` (`--site-name` / `SITE_NAME`), `""` — не задано |
| `primaryEvent` | первостепенное событие гостя (объект события; его `domId`, `domId` его места и программы — `""`: в разметке оно само не выводится) |
| `sections[]` | видимые гостю секции по порядку |

**Секция:** `id`, `type` (`cover` / `custom`), `domId`, `titleId`, `title`,
`titleHidden`, `align`, `width`, `note` (приписка гостя), `widgets[]`, а у
обложки ещё `eyebrow`, `event` (первостепенное событие), `background` (фото на
фоне — объект медиа или `null`) и `backgroundFocus` (значение из перечисления,
по умолчанию `center`; у обычной секции — `""`). Все эти поля есть у секций
обоих типов, лишние — пустые. Фото фона публикуется, как любое показанное
медиа, под именем-хэшем.

**Виджет:** `type`, `domId`, `labelledBy` (`titleId` своей секции) и поля типа:

| Тип | Поля |
|---|---|
| `text` | `text` (готовая строка), `variant` |
| `date` | `event`, `countdown`, `calendar`, `showEventTitle` (гостю видно больше одного события) |
| `events` | `items[]` (события), `count`, `multiple`, `primaryDomId` (`domId` карточки первостепенного события или `""`) |
| `location` | `location` (место, `nested: false`) |
| `schedule` | `items[]` (пункты), `nested: false` |
| `media` | `items[]` (медиа), `layout` |

**Событие:** `id`, `domId`, `title`, `description`, `note` (приписка гостя),
`isMain`, `isPrimary`, `kind` (`primary` / `regular`), `startISO`, `endISO`
(окончание: `end` или начало плюс шесть часов; на странице — только в
`data-events-end`), `dateText` («15 июня 2030»), `timeText` («16:00»),
`whenText` («Суббота, 15 июня 2030, 16:00»; с `showEnd` —
«…, 16:00–23:30»), `tabText` («16:00» или «15 июня, 16:00», если события гостя
в разные дни), `icsPath` (`/assets/<mediaDir>/<hash>.ics` — календарный файл
события, [5](#5-что-получается-в-dist-и-что-проверяется)), `location` (место,
`nested: true`), `program` — `{domId, items[], nested: true}` или `null`, если
программы нет.

**Место:** `id`, `domId`, `ready`, `name`, `address`, `description`,
`mapLinks` (`google`, `yandex`, `apple` — готовая ссылка или `""`),
`hasMapLinks`, `photos[]` (медиа), `directions` (медиа или `null`), `compact`,
`nested`. У необъявленного места (`ready: false`) все поля пустые.

**Медиа:** `id`, `type` (`image` / `video`), `isVideo`, `src`, `posterSrc`,
`thumbSrc` (`thumb`, иначе постер, у фото — сам файл), `width`, `height` (`""`,
если размер неизвестен), `ratio` (`"w / h"`), `durationText` («0:20»), `label`
(«Видео: <alt>, 0:20»), `alt`. Адреса — с именами-хэшами
([3.4](#34-каталог-медиа-и-имена-файлов)), имена файлов из данных в них не
попадают.

**Пункт программы:** `time`, `title`, `text`.

**Хуки скрипта в разметке виджета `events`.** Скрипт страницы (модуль `events`)
находит свои элементы только по этим атрибутам; тексты пометок лежат в
разметке, своих строк у скрипта нет.

| Хук | Где | Смысл |
|---|---|---|
| `data-events` | корень виджета | экземпляр переключателя |
| `data-events-primary` | корень | `primaryDomId`: запасной выбор, если время не читается |
| `data-events-tablist` | список вкладок | в разметке скрыт `hidden`, скрипт показывает его последним шагом |
| `data-events-tab` | вкладка (`button`) | `aria-controls` — `domId` карточки |
| `data-events-panel` | карточка события | панель; роль `tabpanel`, `tabindex` и `aria-labelledby` на вкладку ставит скрипт |
| `data-events-start`, `data-events-end` | карточка | `startISO` и `endISO` — моменты со смещением |
| `data-events-when="past"` / `"now"` | во вкладке и в строке «когда» карточки | пометки «прошло» / «идёт сейчас», скрыты `hidden` |

Состояния, которые ставит скрипт, — для стилей: у вкладки
`aria-selected="true"` и `tabindex="0"` (только у выбранной), у вкладки и
карточки — классы `is-past` (событие закончилось) и `is-now` (идёт); у
неактивных карточек — `hidden`; у списка вкладок — CSS-переменная
`--events-count` (число вкладок, через CSSOM — атрибута `style` в разметке
нет). При любой ошибке скрипт возвращает вид без него.

### 4.5. Ссылки на карты

У каждой карты берётся первое заданное: идентификатор, затем запрос этой
карты. Не задано ни то ни другое — кнопки этой карты нет, даже если у места
есть `geo`.

| Карта | Идентификатор | Запрос |
|---|---|---|
| Google | `https://www.google.com/maps/search/?api=1&query=<запрос или название>&query_place_id=<googlePlaceId>` | `https://www.google.com/maps/search/?api=1&query=<googleQuery>` |
| Яндекс | `https://yandex.ru/maps/org/<yandexOrgId>` или `https://yandex.ru/maps/geo/<yandexGeoId>/` | `https://yandex.ru/maps/?text=<yandexQuery>&ll=<lng>,<lat>&z=16` |
| Apple | `https://maps.apple.com/place?place-id=<applePlaceId>&coordinate=<lat>,<lng>&name=<название>` | `https://maps.apple.com/search?query=<appleQuery>&center=<lat>,<lng>` |

- **Google** требует `query` и рядом с `query_place_id`: он используется,
  только если идентификатор не найден. Туда идёт `googleQuery`, иначе название,
  иначе координаты, иначе адрес. Подсказки района у поиска Google нет — город
  пишут в самом запросе;
- **подсказка района** — `ll` у Яндекса (сначала долгота) и `center` у Apple —
  добавляется, только если у места есть `geo`; без него в ссылке один запрос;
- **Apple**: `coordinate` и `name` рядом с `place-id` — запасной вариант, если
  идентификатор не узнан; каждый добавляется, только если он есть;
- запросы, названия и идентификаторы кодируются целиком (UTF-8, пробел —
  `%20`), поэтому `&`, `#`, `?`, кавычки и кириллица ссылку не ломают.

Если ни одной ссылки нет, блока кнопок нет вовсе. Все внешние ссылки идут с
`target="_blank" rel="noopener noreferrer"` — это проверяется на готовых
страницах.

### 4.6. Заглушка

`stub.html` данных не получает вовсе: единственные подстановки, которые в ней
разрешены, — `{{faviconPath}}` и `{{faviconType}}`. Любая другая конструкция
шаблона в заглушке — ошибка сборки. Заглушка публикуется двумя файлами,
`index.html` и `404.html`, побайтно одинаковыми.

### 4.7. Фрагменты секций и виджетов

Страница собирается из упорядоченного списка секций, секция — из виджетов.
Разметка каждого вида лежит в своём фрагменте; `template.html` включает
`partials/sections`, а тот — секции по типу. Фрагменты читают дерево страницы
([4.4](#44-дерево-страницы)); тесты рендерят их и на вручную составленных
деревьях, и на деревьях, которые строит сборка.

```
fragments/
  partials/sections.html     все секции подряд — готовое содержимое <main>
  sections/cover.html        обложка: единственный h1 (имена пары), дата, фото на фоне; за ней верхняя панель
  sections/custom.html       каркас обычной секции
  widgets/text.html          текст: variant body | lead | signature
  widgets/date.html          дата события (по умолчанию первостепенного), таймер, кнопка календаря
  widgets/events.html        события: список вкладок (скрыт без скрипта) и карточки
  widgets/location.html      карточка места
  widgets/schedule.html      программа отдельным виджетом (пункты — h3)
  widgets/media.html         галерея: layout grid | ribbon | single
  media/image.html           плитка фото
  media/video.html           плитка видео: постер, значок ▶, длительность
  partials/section-head.html заголовок секции (h2, при titleHidden — visually-hidden)
  partials/section-note.html приписка гостя в конце секции
  partials/location-card.html место: полная, компактная, необъявленное
  partials/map-links.html    кнопки карт
  partials/schedule.html     программа: в карточке события пункты h5, в виджете — h3
  partials/countdown.html    таймер (скрыт до запуска скрипта)
```

**Имя файла = тип.** Каркас выбирает фрагмент по полю `type` текущего
элемента: `include:sections/{{.type}}`, `include:widgets/{{.type}}`,
`include:media/{{.type}}`. В `sections/`, `widgets/` и `media/` лежат только
выбираемые фрагменты, общие куски — в `partials/`, поэтому данные не могут
выбрать вспомогательный фрагмент. Первая строка каждого фрагмента —
комментарий «ожидает в `.` …» с перечнем полей, которые он читает; из готовой
страницы он удаляется, как все комментарии. Фрагмент читает только поля
дерева страницы, а дерево содержит их всегда (пустая строка, `[]`, `false`
или `null` вместо отсутствующего значения).

**Каркас секции** (`sections/custom.html`):

```html
<section class="section section--{{.align}}" id="{{.domId}}" aria-labelledby="{{.titleId}}">
  <div class="container container--{{.width}}" data-reveal>
    <!-- include:partials/section-head -->
    <div class="stack section__body">
      <!-- each:.widgets --><!-- include:widgets/{{.type}} --><!-- endeach -->
      <!-- include:partials/section-note -->
    </div>
  </div>
</section>
```

Модификатор класса подставляется из поля только для проверенных перечислений:
`align` (`start` | `center`), `width` (`narrow` | `wide`), `variant`,
`layout`, `kind` (`primary` | `regular`), `backgroundFocus` (фокус фото на
обложке: `cover__photo--top` и т. п.). Остальные различия — парами
`if:x` / `if:!x`.

**DOM-id** строит сборка из пути в конфигурации, фрагменты только дописывают
постоянные суффиксы. Части пути и суффиксы соединяются через `--`: в id из
данных двух дефисов подряд не бывает, поэтому разные пути не дают одинаковых
id.

| Что | id |
|---|---|
| секция | `s-<секция>` |
| заголовок секции | `s-<секция>--title` |
| виджет | `s-<секция>--w<N>`, N — позиция виджета в конфигурации с 1 (скрытые виджеты тоже считаются) |
| событие | `<родитель>--e-<событие>`, родитель — виджет даты или событий (`s-where--w1--e-dinner`) или обложка (`s-cover--e-dinner`); вкладка `…--tab`, заголовок карточки `…--title` (дописывает фрагмент) |
| программа события | `<событие>--program` (строит сборка) |
| место | `<событие или виджет места>--l-<место>` (`s-where--w1--e-dinner--l-manor`) |
| `primaryEvent` в корне дерева, его место и программа | `""` — в разметку они сами не выводятся |

Id из реестров сами по себе не используются: одно событие может стоять на
странице дважды (в виджете даты и среди событий), а путь уникален всегда. На
всякий случай сборка всё равно проверяет дерево каждой страницы и при повторе
id останавливается с ошибкой.

**Уровни заголовков:** h1 — обложка; h2 — секция; h3 — событие, название
места в виджете места, пункты отдельного виджета программы; h4 — место
внутри события и подзаголовок «Программа»; h5 — пункты программы события.
Кусок, который встречается на разной глубине (карточка места, программа),
выбирает тег по признаку `nested`. У виджетов своих заголовков нет: блок со своим
заголовком — отдельная секция.

**Обложка и верхняя панель.** При прокрутке обложка сворачивается в панель у
верхнего края окна: текст обложки и фото на ней гаснут, панель с одной
строкой «имена · дата» проявляется и прилипает к верху. Панель — отдельный
элемент сразу за обложкой, в том же фрагменте:

```html
<section class="cover" id="{{.domId}}" aria-labelledby="{{.titleId}}" data-cover> … </section>
<div class="cover-bar" aria-hidden="true" data-cover-bar>
  <div class="container cover-bar__inner"><span class="cover-bar__title">{{coupleNames}}</span><span class="cover-bar__sep">·</span><span class="cover-bar__date">{{.event.dateText}}</span></div>
</div>
```

| Хук / маркер | Смысл |
|---|---|
| `data-cover` | обложка — то, по прокрутке чего считается сворачивание |
| `data-cover-bar` | панель: копия имён и даты, скрыта от диктора (`aria-hidden`), фокусируемого в ней нет, поэтому h1 на странице по-прежнему один |
| `html.cover-bar-on` | маркер, который ставит модуль `coverBar` скрипта страницы; только под ним панель видна, а переход по якорю отступает на её высоту (`scroll-padding`) |
| `--cover-progress` | прогресс сворачивания 0…1 на обложке и панели для браузеров без временных шкал прокрутки CSS (`animation-timeline`, `timeline-scope`; iOS ≤ 18): его пишет модуль `coverBar`, раз в кадр, через CSSOM. Там, где шкалы есть, CSS гасит и проявляет вуаль, текст обложки и панель тремя анимациями `opacity` прямо по шкале, а модуль только ставит маркер |

Панель стоит в потоке с отрицательным отступом на свою высоту и места не
занимает: её появление раскладку не сдвигает. Без скрипта обложка неподвижна
и панели нет; при «Уменьшении движения» обложка от прокрутки не меняется, а
панель появляется сразу, когда обложка ушла; при печати панели нет, обложка
развёрнута.

**Прокручивает body, а не документ (сенсорный экран).** На сенсорном экране
(`@media screen and (pointer: coarse)`) у страницы приглашения
(`html.invitation`, секция 3 `app.css`) `<html>` и `<body>` — ровно по окну,
`<html>` не прокручивается (`overflow: hidden`), прокручивается `<body>`
(`overflow-y: auto`). Так содержимое обрезается по краю `body`, и ничего из
прокрученного не видно над окном раскладки — под полупрозрачной шапкой
встроенного браузера Telegram на iOS и строкой состояния Safari на iOS 26 (см.
[6.10](#610-как-проверять-стилизацию)). Панель прилипает к верху `body`, шкала
обложки идёт по его прокрутке. На десктопе (основное устройство ввода — мышь
или тачпад) документ прокручивается как обычно: клавиатура прокручивает
страницу сразу после загрузки, перезагрузка сохраняет позицию. Какой режим
включён, решает основное устройство ввода: ПК с сенсорным экраном и мышью
обычно получает прокрутку документа, iPad с клавиатурой — прокрутку `body`.
Скрипты и стили страницы поэтому работают с обоими видами прокрутки:

- прокрутку страницы читать у того, кто прокручивает: у `document.body`
  (`scrollTop`), если его `overflow-y` не `visible`, иначе у окна
  (`window.pageYOffset`, в режиме `body` всегда 0);
- событие `scroll` элемента до `window` не всплывает: слушатель на `window` —
  с `capture: true` (и снимается с тем же флагом);
- отступ под панелью (`scroll-padding-block-start`) и блокировка прокрутки под
  окном просмотра заданы и для `body`;
- ширина полосы прокрутки (отступ под окном просмотра) считается и у `body`;
- печать — прежний документ: правила только для экрана. Заглушка и
  витрина класса `invitation` не имеют и прокручиваются как обычно.

**Метка появления `data-reveal`** — ровно одна на секцию, в каркасе, на
контейнере «заголовок + тело». Её нет на обложке и панели (у них своя анимация), на
виджетах, пунктах списков, плитках, карточках событий, списке вкладок,
таймере и приписках: вложенные метки дали бы две вспышки, а элемент, который
скрывает скрипт или атрибут `hidden`, появился бы с миганием. Тест проверяет
правило и по файлам фрагментов, и по готовым страницам.

**Без скрипта видно всё:** список вкладок событий, таймер и пометки «прошло» /
«идёт сейчас» скрыты атрибутом `hidden` и показываются скриптом (верхняя
панель — копия обложки, без скрипта её просто нет); карточки
событий идут подряд, первостепенная — в рамке акцентом; плитки — обычные
ссылки на файлы. Тексты интерфейса («Добавить в календарь», «Программа»,
«Подробности появятся на этой странице позже.») — во фрагментах, у скриптов
своих строк нет.

**Как добавить тип виджета:**

1. Файл `fragments/widgets/<тип>.html` с одним корневым элементом
   `class="widget <тип>-widget"` (и `id="{{.domId}}"`, если нужны якорь или
   ARIA-связи) и комментарием-контрактом в первой строке.
2. Тип и его поля — в проверке данных (`WIDGET_TYPES`, `WIDGET_FIELDS` в
   `tools/_schema.py`) и в построении дерева страницы (`tools/_page.py`);
   описание — в разделах [3.2](#32-sitejson--общие-данные) и
   [4.4](#44-дерево-страницы).
3. Строка в таблице контракта `WIDGET_FIELDS` в
   `tests/test_fragments_contract.py` (список типов тест берёт из
   `tools/_schema.py` и сверяет с файлами `fragments/widgets/`), пример виджета
   в `widget_variants()`.
4. Стили — подраздел «Виджет: <тип>» секции 6 `app.css`, только токены.
5. Демонстрация разметкой в витрине `styleguide.html` — в своём блоке
   `<!-- sg:<компонент> --> … <!-- /sg:<компонент> -->`.

## 5. Что получается в `dist/` и что проверяется

```
dist/
  index.html                    заглушка
  404.html                      та же заглушка, байт в байт
  i/<token>/index.html          страница приглашения (и больше ничего в каталоге)
  assets/app.css, app.js
  assets/favicon.svg            иконка (из токенов или своя из каталога медиа)
  assets/og.png                 нейтральная картинка предпросмотра — только у сайта без обложки
                                или с --no-link-preview-image
  assets/<mediaDir>/<hash>.<ext>  медиа, показанные хотя бы на одной странице
  assets/<mediaDir>/<hash>.jpg  картинка превью ссылки: титульник (или своя og.* из каталога медиа)
  assets/<mediaDir>/<hash>.ics  календарный файл: по одному на событие, видимое хотя бы одному гостю
  _headers                      заголовки ответа (раздел 9)
  robots.txt                    Disallow: /
```

**Календарный файл** — один на событие **для всего сайта**: при трёх событиях
их три, какой бы ни была рассылка. Файл получает только событие, которое видно
хотя бы одному гостю; событие, скрытое от всех, файла не получает, а общего
файла со всеми событиями нет. Ссылка «Добавить в календарь» на файл события
есть только на страницах тех, кому событие видно.

- **Имя** — первые 16 шестнадцатеричных знаков
  `HMAC-SHA256(ключ, содержимое файла)`, где ключ — `sha256` от токенов всех
  приглашений, отсортированных и соединённых переводом строки:
  `/assets/<mediaDir>/6f1c…e2a9.ics`. Простой хэш содержимого не годится:
  содержимое угадывается (название, время, место события), и такое имя можно
  подобрать перебором запросов к сайту. С ключом для вычисления имени нужно
  знать **все** токены, а тот, кто их знает, и так откроет все страницы.
  Значит, файл скрытого события защищён ровно как страница гостя, и эта защита
  зависит от стойкости токенов: короткий угадываемый токен ослабляет и её
  ([3.3](#33-правила-токенов)). Новых полей в данных нет, сборка остаётся
  воспроизводимой. Новое приглашение меняет имена всех календарных файлов —
  это безвредно: страницы пересобираются вместе с ними.
- **Содержимое** — одно событие (`VEVENT`): `SUMMARY` — заголовок записи в
  календаре, «имена пары · название события», например «Алиса и Боб ·
  Праздничный ужин»: имена — `coupleNames` из `site.json` (то же, что в
  заголовке обложки), разделитель — константа `ICS_SUMMARY_SEPARATOR` в
  `build.py`; `DTSTART` и `DTEND` в UTC, `LOCATION` — «название, адрес» места,
  если оно объявлено, `UID` — `sha256(mediaDir \n eventId \n start)[:32]@invitation`.
  Запятые, точки с запятой и обратные косые черты в тексте экранируются, строки
  длиннее 75 байт переносятся. Данных гостя (обращения, приписок, токена) в
  файле нет, поэтому один файл годится всем, кто видит событие. Имена пары —
  общие данные сайта; вне страниц гостей они есть только в календарных файлах,
  а имена этих файлов, как сказано выше, защищены так же, как страницы.
- **`DTEND`** — `end` события или, без него, начало плюс шесть часов
  ([3.2](#32-sitejson--общие-данные)); у всех гостей оно одно.
- **Если событие изменилось**, меняется и содержимое, а с ним имя файла:
  страницы следующей сборки ссылаются на новый файл, старого в `dist/` больше
  нет. Новое название, имена пары, окончание или объявленное место при том же начале
  сохраняют `UID`. Но `DTSTAMP` в файле постоянный, а `SEQUENCE` растёт только
  когда место объявлено, поэтому обновит ли календарь гостя прежнюю запись при
  повторном добавлении, зависит от календаря: некоторые оставят старую или
  создадут вторую. Новое начало даёт новый `UID`: кто уже добавил событие,
  получит вторую запись и старую удалит сам.

**Медиа** публикуются под именами-хэшами содержимого
([3.4](#34-каталог-медиа-и-имена-файлов)); если страницы не показывают ни
одного медиа, в `assets/<mediaDir>/` лежат только календарные файлы.

Больше в сборке нет ничего: ни JSON с данными, ни списков токенов, ни source
maps, ни файлов витрины, ни фрагментов шаблона, ни страницы-превью с её `preview.css`, ни `.md`, ни
точечных файлов.

После записи сборка проверяет **готовое дерево** и падает с перечнем проблем,
если что-то не так (сообщения не цитируют текст страниц; выводится не больше 25
проблем):

- **состав** — только ожидаемые файлы и каталоги; в `i/` — по одному каталогу
  на приглашение, в нём только `index.html` (календарный файл там — ошибка); в
  `assets/` только разрешённые типы файлов (`.css`, `.js`, `.woff2`, `.ico`,
  `.txt`, картинки, `.mp4`) и из подкаталогов — только `fonts/` и каталог медиа;
  в `assets/<mediaDir>/` — ровно опубликованные имена-хэши показанных медиа и
  календарных файлов событий (файл под исходным именем, лишний хэш или лишний
  `.ics` — ошибка), а без них этого каталога нет;
  `.json`, `.map`, `.py`, `.md` не публикуются нигде; символические ссылки
  запрещены; обязательные файлы на месте;
- **размер** — ни одного файла больше **25 MiB** (ограничение хостинга на файл);
- **HTML** — не осталось синтаксиса шаблона и комментариев; нет внешних
  ресурсов, inline-скриптов и обработчиков, встраиваемых документов, CDATA и
  инструкций обработки; внешние ссылки — только на три картографических сервиса
  и только с `target`/`rel`; каждый локальный адрес указывает на существующий
  файл сборки; нет текста, который разборщик видит текстом, а браузер прочитал
  бы как разметку (см. [4.3](#43-чего-нельзя-в-шаблоне));
- **CSS** — `url()` и `@import` указывают на существующие локальные файлы;
  CSS-escape-последовательности, которыми можно спрятать адрес, запрещены;
- **SVG** — ни скриптов, ни стилей, ни обработчиков, ни `<foreignObject>`, ни
  сущностей, ни внешних ссылок.

**Сборка воспроизводима**: одни и те же данные, медиа и код дают побайтно
одинаковый `dist/` (в календарном файле фиксированный `DTSTAMP`, порядок файлов
не зависит от файловой системы) — **на одной машине с одной версией Chrome и
одними шрифтами**: картинку превью рисует браузер, и на другой машине или
другой версии Chrome она (а с ней и её имя-хэш) может отличаться
([6.7](#67-иконка-картинка-предпросмотра-и-цвет-интерфейса-браузера)). Это проверяется в CI сравнением контрольных сумм
двух сборок подряд.

## 6. Дизайн-система — раздел для этапа стилизации

Весь внешний вид сайта задан **токенами** — именованными CSS-переменными в одном
месте: секция 1 файла `assets/app.css`. Компоненты (секции 3–8 того же файла)
используют только токены, `calc()` над ними и ключевые слова; «сырых» значений
в них нет. Поэтому смена палитры, шрифтов, размеров и пропорций — это правка
секции 1, без единого изменения в разметке и в скриптах.

Текущие значения — временные. Они помечены в коде пометкой `TEMP` и подобраны
нейтрально (системный шрифт, серо-синяя палитра с контрастом не хуже WCAG AA),
чтобы проверить раскладку и читаемость, а не чтобы определить стиль.

Файл `app.css` разбит на пронумерованные секции: 1 Tokens, 2 Fonts, 3 Base,
4 Layout primitives, 5 Components, 6 Page layout, 7 Motion & reveal,
8 Gallery & lightbox.

### 6.1. Как устроен токен: пара «мобильный/десктоп» и производный

Параметр, который может отличаться между телефоном и десктопом, задан **парой**
токенов, а компоненты используют только **производный** токен без суффикса:

```css
--text-2xl-mobile: 30;     /* число: px при размере шрифта 16px */
--text-2xl-desktop: 42;
--text-2xl: clamp(…);      /* это и читают компоненты */
```

Производный получается одним из двух способов:

- **плавная интерполяция** `clamp()` между опорными ширинами `--vw-min` (360) и
  `--vw-max` (1440) — для размеров, отступов, ширин, амплитуд движения. Значения
  пары хранятся безразмерными числами, потому что `calc()` не умеет делить длину
  на длину; в длину их превращает формула. **Порядок значений в паре любой**:
  мобильное может быть и больше десктопного — границы `clamp()` берутся как
  `min()`/`max()` от пары;
- **переопределение на границе раскладки** — в блоке `@media (min-width: 48em)`
  в конце секции 1. Так заданы величины, которые нельзя интерполировать: число
  колонок (`--grid-columns`, `--gallery-columns`, `--gallery-columns-venue`),
  пропорции изображений (`--ratio-photo`, `--ratio-gallery`, `--ratio-scheme`),
  доля высоты экрана под обложку (`--cover-height-ratio`).

Параметры без пары (цвета, радиусы, тени, длительности, интерлиньяж) при
необходимости переопределяются в том же блоке `@media`.

Чтобы поменять параметр, правят **значения пары**, а не формулу производного
токена.

### 6.2. Единицы: что в `rem`, что в `px` и почему

Вопрос к каждому токену один: должно ли значение расти, когда человек увеличил
шрифт в системе или в браузере?

| Единица | Что в ней задано | Почему |
|---|---|---|
| `rem` | типографическая шкала, ширины контейнеров, размер иконок, предел ширины ячейки таймера, пороги `@container` | длина строки и пропорция «иконка — подпись» сохраняются при любом размере шрифта |
| `rem` с потолком от ширины окна | отступы и зазоры: `--space-*`, `--space-section`, `--container-gutter`, `--grid-gap`, `--countdown-gap` | на широком экране отступы растут вместе с текстом, а на телефоне не съедают ширину: `min(<формула в rem>, mobile / --vw-min * 100vw)` |
| `px` | волосяные линии и рамки, кольцо фокуса, радиусы, тени, `--tap-min`, амплитуды движения | это физические величины: цель нажатия 44 px — требование доступности, а не стиль, и расти вместе со шрифтом ей незачем |
| `em` / `ch` | трекинг, ширины «в знаках» | следуют за шрифтом самого элемента |

При размере шрифта по умолчанию и ширине окна от `--vw-min` все формулы дают
ровно числа из пар.

Два ограничения на значения пар — иначе формулы работают не так, как задумано:

- **типографика**: большее значение пары ≤ 2,5 × меньшего, иначе масштаб 200 % в
  браузере не увеличит текст вдвое;
- **отступы с потолком**: мобильное значение > 0, десктопное ≤ 4 × мобильного,
  иначе потолок сработает и при обычном размере шрифта.

### 6.3. Перечень токенов

Группировка в таблице ниже — своя, для чтения; витрина группирует по своим

«Прочее»). Совпадает состав, а не названия групп.

| Группа | Токены | Назначение | Пары м/д |
|---|---|---|---|

`@media (prefers-reduced-motion: reduce)` длительности и дистанции обнуляются

отключаются, а сворачивание обложки в панель идёт ступенькой (прогресс
прокрутки не зависит от длительностей).

### 6.4. Границы раскладки и пороги контейнеров

`var()` не работает в условиях `@media` и `@container`, поэтому пороги **дважды
записаны в файле**: токеном (его читает витрина и по нему ориентируется
человек) и числом в самом условии. **Меняя токен, надо поменять и число в
условии** — рядом с каждым условием стоит комментарий, какому токену оно должно
соответствовать.

| Порог | Токен | Где условие | Что меняется |
|---|---|---|---|
| Граница раскладки | `--bp-layout: 48em` | `@media (min-width: 48em)` в конце секции 1; `@media not all and (min-width: 48em)` в секции 8 | одна колонка → две, пропорции изображений, доля высоты обложки; лента галереи только на мобильном |
| Таймер в ряд | `--countdown-inline-min: 19.5rem` | `@container (min-width: 19.5rem)` в секции 5 | четыре ячейки в ряд вместо 2×2 |
| Таймер в колонку | `--countdown-stack-max: 9rem` | `@container (max-width: 9rem)` в секции 5 | одна колонка при очень крупном шрифте |
| Программа дня | `--schedule-inline-min: 18.5rem` | `@container (max-width: 18.5rem)` в секции 6 | время встаёт над описанием, а не слева |

`@container` меряет не окно, а место, доставшееся компоненту: контейнерами
объявлены `.container` и элементы сетки (`.grid > *`, секция 4). Поэтому
таймер и программа дня одинаково хорошо выглядят и в узкой колонке двухколоночной секции, и во всю ширину. Браузер без поддержки
`@container` показывает таймер 2×2, а программу дня — в строку.

`48em` в медиазапросе — это 768 px при шрифте браузера по умолчанию; `em` в
условии `@media` считается от **исходного** размера шрифта браузера, поэтому при
увеличенном шрифте две колонки включаются позже — когда для них действительно
есть место.

### 6.5. Страница следует системному размеру шрифта

Размер шрифта корня страница **не задаёт** — его определяет пользователь:
настройкой браузера, а на телефоне системным размером текста.

- **Chromium (Android и встроенные браузеры мессенджеров)** — мета-тег
  `<meta name="text-scale" content="scale">` в `template.html`, `stub.html` и
  `styleguide.html`;
- **iOS и iPadOS** — правило в секции 3:
  `@supports (font: -apple-system-body) and (-webkit-touch-callout: default) { :root { font: -apple-system-body; } }`.
  Это единственный способ получить системную настройку «Размер текста»
  (Dynamic Type); условие `-webkit-touch-callout` отсекает Safari на macOS, где
  тот же стиль дал бы корню 13 px. При стандартной настройке `1rem` на iOS —
  17 px, в остальных браузерах — 16 px.

Чего делать нельзя:

- **задавать размер шрифта корня в пикселях** (`html { font-size: 16px }`) —
  это отменяет системную настройку и ломает всю шкалу;
- **вешать шрифтовые свойства на `html`** — сокращённое свойство `font:
  -apple-system-body` сбрасывает на `:root` гарнитуру, насыщенность и
  интерлиньяж, поэтому все они заданы на `body` из токенов и от корня не
  наследуются;
- убирать `-webkit-text-size-adjust: 100%` с `html`.

### 6.6. Ограничение на формат цвета

Цвета читает не только браузер, но и сборка: из токенов рисуются иконка и
картинка предпросмотра, а цвет `--color-cover-veil` становится цветом интерфейса
браузера над страницей ([6.7](#67-иконка-картинка-предпросмотра-и-цвет-интерфейса-браузера)).
Она понимает:

- `#rgb`, `#rgba`, `#rrggbb`, `#rrggbbaa`;
- `rgb(…)` и `rgba(…)` — и через запятую, и в записи `rgb(14 16 18 / 78%)`;
- `var(--другой-токен)`, в том числе цепочкой и с запасным значением.

`hsl()`, `oklch()`, `lab()`, `color-mix()` и **именованные цвета**
(`white`, `tomato`) она не понимает. Такое значение в любом из цветовых токенов
`--color-bg`, `--color-surface`, `--color-surface-sunken`, `--color-text`,
`--color-text-muted`, `--color-accent`, `--color-on-accent`, `--color-line`,
`--color-cover-veil` (в том числе в токене, на который он ссылается через
`var()`) останавливает сборку с понятным сообщением:

```
error: assets/app.css: design token '--color-accent': unsupported colour 'oklch(70% 0.15 60)' (expected #rgb, #rrggbb, #rrggbbaa, rgb() or rgba()) (the colour of the browser interface, the icon and the link preview image are taken from the design tokens)
build: failed
```

Токены читаются при каждой сборке — даже когда иконка и картинка
предпросмотра свои: цвет интерфейса браузера нужен всегда.

Остальные цветовые токены (оверлеи, тени, выключенные состояния) сборкой не
читаются, но лучше держать весь набор в одной записи. Полупрозрачные цвета
допустимы: сборка сводит их на фон (`--color-bg`, а его — на белый).

Читаются только правила `:root` верхнего уровня; значения, переопределённые
внутри `@media`, сборка не видит — картинки и цвет интерфейса всегда берутся
по базовым значениям.

### 6.7. Иконка, картинка предпросмотра и цвет интерфейса браузера

Иконка и картинка предпросмотра рисуются при каждой сборке и в репозитории не хранятся:

- `favicon.svg` — скруглённый квадрат цвета `--color-accent` со знаком цвета
  `--color-on-accent`;
- **картинка превью ссылки — титульник**: обложка сайта, снятая headless
  Chrome ([3.5](#35-своя-иконка-и-своя-картинка-предпросмотра)). Страница-превью
  — `preview.html` с тем же фрагментом обложки и `app.css`, плюс
  `assets/preview.css` (обложка ровно в кадр, текст в центральном квадрате,
  панель скрыта). Chrome запускается с профилем во временном каталоге (`TMPDIR`),
  без сети наружу: страница и её файлы отдаются с `127.0.0.1`; управление — по
  протоколу отладки через канал (`--remote-debugging-pipe`), без сторонних
  пакетов. Скрипты страницы выключены, `prefers-reduced-motion: reduce`,
  полос прокрутки нет; снимок повторяется, пока два подряд не совпадут.
  Рендер один на сборку, около 1–2 с;
- `og.png` 1200×630 — нейтральная композиция из `--color-bg`, `--color-surface`,
  `--color-line`, `--color-text` и `--color-accent`, без имён и дат: для сайта
  без обложки и для сборки с `--no-link-preview-image`.

**Шрифты и воспроизводимость титульника.** Пока своих шрифтов нет, титульник
рисуется системным шрифтом машины сборки: на Mac — как на iPhone, на
Linux-раннере выкладки — другим начертанием (владельцев это устраивает). С
подключёнными `woff2` ([6.8](#68-локальные-шрифты)) картинка подхватит их сама
и совпадёт везде. На одной машине с одной версией Chrome две сборки дают
побайтно одинаковую картинку; между машинами и версиями Chrome — не
обязательно (версию Chrome выкладка не фиксирует).

Посмотреть, не собирая сайт: `python3 tools/gen_assets.py --out /tmp/assets`.
Заменить своими файлами: положить их в каталог медиа
(см. [3.5](#35-своя-иконка-и-своя-картинка-предпросмотра)).

PNG пишется своим кодировщиком на стандартной библиотеке (`zlib`, фиксированный
уровень сжатия, без метаданных и временных меток). На одной и той же версии
Python результат побайтно одинаков; на разных версиях `zlib` может отличаться
размер файла — на вид картинки это не влияет, но два `og.png`, собранные разными
версиями Python, могут не совпасть побайтно.

**Цвет интерфейса браузера.** Всё, что браузер рисует над страницей и за её
краями, окрашивается в цвет свёрнутой панели обложки — токен
`--color-cover-veil` (сейчас он равен `--color-surface`). Два места:

- `<meta name="theme-color" content="{{themeColor}}">` в `template.html`.
  Значение подставляет сборка: берёт токен (с цепочкой `var()`), сводит его к
  непрозрачному `#rrggbb` и кладёт в поле корня `themeColor`. Своего цвета в
  шаблоне нет — сменили токен, пересобрали;
- холст страницы: `html.invitation { background-color: var(--color-cover-veil) }`
  (секция 3 `app.css`, класс `invitation` у `<html>` ставит `template.html`).

Где это видно:

- **Android Chrome** — адресная строка и строка состояния цвета панели, в том
  числе пока обложка развёрнута;
- **Safari на iOS 15–18** — область под строкой состояния. Safari 26 тег не
  применяет и берёт цвет со страницы сам — у прилипшей панели и её заливки
  (см. [6.10](#610-как-проверять-стилизацию));
- **перетягивание за верхний и нижний край** — там виден холст. WebKit по
  умолчанию берёт цвет «под страницей» из фона `html` и `body`, в том числе во
  встроенных браузерах приложений на iOS. Внизу при перетягивании тоже цвет
  панели, а не белый фон страницы, — это осознанно;
- **встроенный браузер Telegram**: на iOS он `theme-color` не читает и свою
  верхнюю «стеклянную» шапку красит сам, а страницу кладёт под неё. Под шапкой
  виден холст цвета панели: прокручивается `body`, и содержимое страницы туда
  не попадает ([6.10](#610-как-проверять-стилизацию)). **Известное
  ограничение**: цвет самой шапки задаёт Telegram — это полупрозрачный
  материал поверх холста, `theme-color` и фон страницы он не читает, поэтому
  шапка чуть светлее и нейтральнее панели обложки. Совпадения не добиться, это
  не исправляется (см. [11.1](#111-что-нужно-проверить-на-настоящих-устройствах));
  на Android без включённого адаптивного цвета браузера (по умолчанию он
  выключен) Telegram красит свою верхнюю панель в цвет своей темы, а при
  включённом берёт цвет со страницы: `tg:theme-accent`, иначе `theme-color`,
  иначе фон `body`.

Когда у `html` есть свой фон, фон `body` на холст больше не переносится и
закрашивает только сам `body`. Поэтому у страницы приглашения `body` не ниже
окна (`min-block-size: var(--viewport-height-dynamic)`): на короткой странице
под содержимым по-прежнему фон страницы, а не цвет панели. Заглушка и
витрина класса `invitation` не имеют — у них холст, как и раньше, цвета `body`.
`color-scheme: only light` на цвет холста не влияет: он задан явно.

Сменить цвет верхней области отдельно от панели: другой токен в
`site_colors_context` (`build.py`) и в правиле `html.invitation` (`app.css`) —
по одной строке.

### 6.8. Локальные шрифты

Внешние шрифты запрещены: со страницы нет запросов на сторонние домены. Чтобы
подключить свой шрифт:

1. положить файлы `woff2` в `/assets/fonts/` (каталог уже есть);
2. раскомментировать и размножить по начертаниям образец `@font-face` в
   секции 2 `app.css`;
3. переключить в секции 1 токены `--font-heading` и/или `--font-body` на новое
   семейство, оставив системный стек последним запасным вариантом:
   `--font-heading: "Invitation Display", var(--font-body);`
4. при необходимости подстроить `--font-weight-*`, `--line-height-*` и
   `--tracking-*`; ступени шкалы менять не требуется.

`font-display: swap` обязателен: текст виден сразу, без «мигания пустотой».
Пути в `url()` — абсолютные от корня (`/assets/fonts/…`); проверка сборки
потребует, чтобы файл существовал.

### 6.9. Что обновлять при рестайлинге

1. **Секцию 1 `app.css`** — значения токенов (пары «мобильный/десктоп» там, где
   они есть). Пометки `TEMP` снимают по мере того, как значения становятся
   окончательными.
2. **Числа в условиях `@media` и `@container`** — если менялись соответствующие
   токены-пороги ([6.4](#64-границы-раскладки-и-пороги-контейнеров)).
3. **Шрифты** — файлы в `/assets/fonts/` и блок `@font-face` в секции 2.
4. **Тему** — `color-scheme` задан значением `only light` и в токенах, и
   мета-тегом `<meta name="color-scheme">` в `template.html`, `stub.html` и
   `styleguide.html`; если окончательная тема тёмная, меняют оба места вместе с
   цветами. `prefers-color-scheme` не используется нигде: у страницы одна
   фиксированная тема, и на принудительное затемнение во встроенных браузерах
   она не реагирует.
5. **Сопутствующие форматы** — ничего не надо делать руками: иконка, картинка
   предпросмотра, цвет интерфейса браузера (`theme-color`) и картинки-заглушки
   для примеров берутся из тех же токенов, а титульник превью ссылки — снимок
   той же обложки: рестайлинг обложки меняет и его (при необходимости
   поправить раскладку кадра в `assets/preview.css`).
   Достаточно пересобрать сайт, а картинки примеров — перегенерировать
   (`python3 tools/gen_example_media.py`).
6. **Витрину** — если появился новый токен или новый компонент. Список токенов
   витрина читает из `app.css` сама, а демонстрации компонентов написаны
   разметкой.
7. **Тесты** — `python3 -m unittest`. Часть тестов знает о дизайн-системе:
   проверяется, что в стилях галереи нет «сырых» значений, а граница раскладки
   в условии совпадает со своим токеном, что генератор изображений читает
   палитру, что в сборку не попадают файлы витрины.

### 6.10. Как проверять стилизацию

- **Витрина** `styleguide.html` ([2.10](#210-витрина-дизайн-системы)) — таблица
  всех токенов с вычисленными значениями (пересчитывается при изменении ширины
  окна), типографическая шкала, раскладка, компоненты и их состояния
  (hover / focus-visible / active / disabled). **Плитки фото и видео** показаны
  плашками вместо картинок (медиафайлов в репозитории нет): значок ▶, фокус,
  hover, длительность и одиночная плитка `.gallery--single`. Ролик в окне
  просмотра витрина только описывает: окно создаёт скрипт, а панель ролика —
  нативная панель браузера, своих стилей и токенов у неё нет. Окно с роликом и
  одиночную плитку в пропорции кадра сверяют на собранной странице с видео
  (подойдёт страница из основного примера).
- **Переключатель масштаба шрифта** в витрине (100 / 125 / 150 / 200 / 330 %) —
  быстрая проверка того, что раскладка не ломается при крупном системном шрифте.
  Настоящая проверка — увеличить шрифт в настройках браузера или системы.
- **Ширины** 360, 390, 768, 1024, 1440, 1920 px и ландшафтная ориентация
  телефона (например, 740×360): не должно быть горизонтальной прокрутки,
  наложений и обрезанного текста, а на десктопе контент не должен растягиваться
  на всю ширину.
- **Сворачивание обложки в панель** — на собранной странице (витрина
  показывает панель только в свёрнутом виде). Медленно прокрутить обложку:
  текст обложки гаснет к доле `--cover-fade-end` прогресса, вуаль фото
  сгущается до полной, панель проявляется начиная с `--cover-bar-fade-start`
  и прилипает к верху, когда от обложки остаётся полоса её высоты; раскладка
  при этом не сдвигается. Проверить на 360 px и 1440 px, в ландшафте и при
  шрифте 200 % (панель выше, имена с многоточием, дата целиком); переход по
  якорю (`#s-where`) — цель ниже панели, а не под ней; с клавиатуры Tab по
  всей странице — фокус не прячется под панелью; окно просмотра фото — поверх
  панели. В Chrome прогресс ведёт CSS (временная шкала прокрутки); путь для
  браузеров без шкал (iOS ≤ 18) проверяют на копии сборки, где в
  `assets/app.css` и `assets/app.js` условие
  `(animation-timeline: --a) and (timeline-scope: --a)` заменено на заведомо
  ложное, например `(not (color: red))`: тогда прогресс пишет скрипт, вид
  должен быть тем же. С «Уменьшением движения» (в DevTools — Rendering →
  `prefers-reduced-motion`) обложка не меняется, панель появляется скачком;
  без JS панели нет; при печати с середины страницы обложка развёрнута,
  панели нет.
- **Область над прилипшей панелью** — встроенный браузер Telegram на iOS
  (плавающая «стеклянная» шапка) и Safari на iOS 26 кладут страницу под свою
  полупрозрачную шапку: окно раскладки начинается у её нижнего края, но
  прокручиваемое содержимое документа WebKit рисует и выше. Всё прилипающее и
  фиксированное он при этом обрезает по окну раскладки, поэтому ни заливка над
  панелью, ни фиксированная полоса, ни тень вверх эту область не закрывают.
  Решение — на сенсорном экране прокрутка `body` вместо документа (см.
  «Прокручивает body, а не документ» в
  [4.7](#47-фрагменты-секций-и-виджетов)): содержимое обрезается по краю
  `body`, а над окном остаётся только холст `html` цвета панели. Проверка в
  Chrome — в режиме мобильного устройства с касанием (DevTools → Device
  Toolbar; протоколом — `Emulation.setTouchEmulationEnabled` и
  `Emulation.setEmitTouchEventsForMouse`, тогда `(pointer: coarse)` верно):
  `document.scrollingElement.scrollTop` и `window.pageYOffset` всегда 0, а
  `document.body.scrollTop` растёт при прокрутке. Без эмуляции касания
  прокручивается документ, как раньше, PageDown сразу после загрузки
  работает. В обоих режимах сворачивание обложки то же, что раньше, в обоих
  приводах (с временными шкалами и на копии с ложным условием, см. выше),
  переход по якорю — цель под панелью, под окном просмотра фон не
  прокручивается, печать — как раньше. Заливка `.cover-bar::before`
  (продолжение панели вверх её цветом на `--viewport-height`) осталась: на
  странице приглашения с прокруткой `body` она уходит за его край и не видна,
  витрина показывает её в обрезающей рамке. Безопасную зону выреза в DevTools
  Chrome можно задать протоколом (`Emulation.setSafeAreaInsetsOverride`):
  панель становится выше на её размер, текст остаётся в нижней полосе.
  Мета-тег `theme-color` полосу внутри страницы не закрывает: Safari 26 его
  не применяет и цвет системной области берёт сам (у панели и страницы), а
  Safari 18 и Android Chrome красят им только свой интерфейс. Зачем он всё же
  есть — для интерфейса браузера и холста за краями страницы
  ([6.7](#67-иконка-картинка-предпросмотра-и-цвет-интерфейса-браузера)).
  Проверка в Chrome: у страницы приглашения `<meta name="theme-color">` равен
  вычисленному `--color-cover-veil`,
  `getComputedStyle(document.documentElement).backgroundColor` — тот же цвет;
  у заглушки и витрины мета-тега нет, фон `html` прозрачный.
- **Проверка «сырых» значений** — в компонентах их быть не должно:

  ```bash
  python3 - <<'PY'
  import re
  src = open('assets/app.css', encoding='utf-8').read()
  start = src.count('\n', 0, src.rindex('   3. Base'))
  body = re.sub(r'/\*.*?\*/', lambda m: '\n' * m.group(0).count('\n'), src, flags=re.S)
  raw = re.compile(r'#[0-9a-fA-F]{3,8}\b|\b(?:rgb|rgba|hsl|hsla|oklch|color-mix)\('
                   r'|(?<![\w.#-])\d*\.?\d+(?:px|rem|em|ms|s|vw|vh|svh|dvh)\b')
  bad = [(n, l.strip()) for n, l in enumerate(body.split('\n')[start:], start + 1)
         if not re.search(r'@media|@container|@supports', l) and raw.search(l)]
  print(len(bad), 'строк с «сырыми» значениями в секциях 3-8')
  for n, l in bad:
      print(' ', n, l)
  PY
  ```

  Команда смотрит на секции 3–8 без комментариев и пропускает строки условий
  `@media` / `@container` / `@supports` — числа в них и есть задокументированное
  исключение. Сейчас она печатает `0`.

## 7. Сторонние библиотеки

Сторонних библиотек нет. Страница работает на двух своих файлах — `app.css` и
`app.js`; видео играет нативный `<video controls>` с панелью браузера
([8.4](#84-плитка-и-окно-просмотра)). Каталога `assets/vendor/` в репозитории нет.

Если библиотека всё же понадобится, её подключают на таких условиях:

- **только локально** — файлы лежат в `assets/vendor/<имя>-<версия>/` и
  подключаются оттуда; каталог `vendor` добавляют в разрешённые каталоги
  `assets/` (`ASSET_DIRECTORIES` в `build.py`): сейчас проверка результата
  пропускает там только `fonts/` и каталог медиа. CDN и любые другие внешние адреса запрещены, в том числе
  те, к которым библиотека обращается сама (иконки, шрифты, «пустые» ролики,
  статистика): такие обращения отключаются её настройками, и это закрепляется
  автотестом;
- **фиксированная версия** — номер версии стоит в имени каталога; источник
  пакета, его контрольная сумма и перечень файлов с их суммами записываются в
  этот раздел;
- **допустимая лицензия** (MIT, BSD, Apache 2.0 и подобные) — её текст лежит
  рядом с файлами как `LICENSE.txt`: файлы `.md` в сборку не публикуются;
- **совместимость с CSP** ([раздел 9](#9-заголовки-приватность-индексация)) —
  без inline-скриптов, `eval` и `new Function`; политику ради библиотеки не
  ослабляют;
- **вес** — весь сторонний код вместе не больше ~150 КБ после gzip; файлы
  `*.map` не кладут;
- **шаблон остаётся обычным HTML** — библиотека улучшает готовую разметку, а не
  строит страницу, и без неё содержимое доступно полностью;
- **медиафайлы** (например, SVG-спрайт иконок) в `vendor` допустимы только
  вместе с осознанным исключением в правиле гигиены репозитория
  ([раздел 10](#10-непрерывная-интеграция)) и тестом на это исключение; `.js`,
  `.css`, `.woff2` и `.txt` под это правило не попадают.

Сборка копирует `assets/` в `dist/` целиком, поэтому вендорные файлы попадут в
сборку любого набора данных, даже если страницы на них не ссылаются.

## 8. Видео

### 8.1. Требования к файлу

- один файл, **не больше 25 MiB** (ограничение хостинга на файл; проверяется
  сборкой);
- H.264 (профиль High, `yuv420p`) + AAC в контейнере `.mp4`, с `+faststart`,
  чтобы воспроизведение начиналось без полной загрузки;
- SDR: HDR-исходник нужно привести к SDR **до** кодирования, иначе на части
  устройств картинка будет выцветшей;
- метаданные исходника (модель камеры, геометка, дата) удаляются;
- ориентация любая: плитка на странице и кадр в окне просмотра принимают
  пропорцию ролика (портретный ролик на десктопе — узкая плитка по центру
  колонки).

### 8.2. Подготовка

Перекодирование (подставьте нужную высоту кадра: `-2` в `scale` подбирает вторую
сторону так, чтобы она осталась чётной):

```bash
ffmpeg -i in.mov -vf "scale=-2:1280" \
  -c:v libx264 -profile:v high -pix_fmt yuv420p -crf 26 -preset slow \
  -c:a aac -b:a 96k -movflags +faststart -map_metadata -1 proposal.mp4
```

Для **портретного** ролика ограничивают высоту (`scale=-2:1280`), для
**ландшафтного** — ширину (`scale=1280:-2`). `-crf` больше → файл меньше и
качество ниже; 23–28 — разумный диапазон.

Если исходник **HDR** (снято на современный телефон), добавьте приведение к SDR
перед масштабированием:

```bash
ffmpeg -i in.mov \
  -vf "format=gbrpf32le,tonemap=hable:desat=0,format=yuv420p,scale=-2:1280" \
  -c:v libx264 -profile:v high -pix_fmt yuv420p -crf 26 -preset slow \
  -c:a aac -b:a 96k -movflags +faststart -map_metadata -1 proposal.mp4
```

Если в вашей сборке `ffmpeg` есть фильтр `zscale` (`ffmpeg -filters | grep
zscale`), точнее получится с ним:
`-vf "zscale=t=linear:npl=100,format=gbrpf32le,zscale=p=bt709,tonemap=hable:desat=0,zscale=t=bt709:m=bt709:r=tv,format=yuv420p,scale=-2:1280"`.
Результат тон-маппинга надо посмотреть глазами: автоматическая проверка тут
невозможна.

Если файл не уложился в 25 MiB: поднять `-crf` (шаг +2 уменьшает файл примерно
на треть), уменьшить сторону кадра или укоротить ролик (`-t 40`). Ориентир:
суммарный битрейт, при котором получается 25 MiB, ≈ 190 000 / длительность в
секундах кбит/с (запас ~10 %), из них ~96 кбит/с уходит на звук. Проверка
результата:

```bash
ls -l proposal.mp4                       # не больше 26 214 400 байт
ffprobe -v error -select_streams v:0 -show_entries stream=width,height \
        -of csv=p=0 proposal.mp4         # → 720,1280
```

Постер — кадр из готового файла (момент выбирают по вкусу):

```bash
ffmpeg -ss 00:00:01 -i proposal.mp4 -frames:v 1 -update 1 -q:v 3 proposal-poster.jpg
```

`-update 1` говорит, что пишется одна картинка, а не последовательность кадров:
без него ffmpeg выдаёт предупреждение про отсутствие шаблона имени вида `%03d`
(файл при этом получается правильный).

Постер должен быть той же пропорции, что и ролик, иначе при загрузке страницы
кадр «прыгнет».

### 8.3. Данные

Ролик — элемент реестра медиа ([3.2](#32-sitejson--общие-данные)):

```json
"media": {
  "proposal": { "type": "video", "file": "proposal.mp4", "poster": "proposal-poster.jpg",
                "width": 720, "height": 1280, "alt": "Видео предложения" } }
```

Показывают его, как и фото, виджетом «Медиа» (`"layout": "single"` — одна
крупная плитка, `grid` и `ribbon` — вместе с фото) или в `photos` места — тогда
он листается в окне просмотра вместе с фотографиями места. Роликов может быть
сколько угодно, у каждого свой размер.

`width`/`height` — те самые числа из `ffprobe`. Они попадают в разметку плитки
(пропорция одиночной плитки, размеры постера, `data-media-ratio` для окна
просмотра): место под кадр резервируется до загрузки, и браузер знает пропорцию
заранее. Если их не задать, сборка возьмёт размер из постера или из самого
`.mp4`; если не получится и так — пропорция 16:9 из токена, что для
вертикального ролика заметно испортит первый экран. Длительность («0:20» на
плитке и в подписи для экранного диктора) сборка читает из файла сама.

Сборка проверяет файл ролика: не `.mp4`, битый или не тот формат — ошибка;
индекс в конце файла (нет `+faststart`), кодек не H.264, HDR, нечитаемая
длительность и постер другой пропорции — предупреждения.

Требования к файлу и данным не зависят от того, как ролик показан на странице.

### 8.4. Плитка и окно просмотра

**На странице** ролик — плитка, как у фотографий: постер (одиночная плитка
`.gallery--single` — в пропорции кадра), по центру круглый значок ▶,
длительность в углу, нажимается вся плитка. Плитка
— обычная ссылка на файл ролика; `<video>` на странице нет, поэтому до нажатия
файл ролика не запрашивается вовсе.

**По нажатию** открывается то же окно просмотра, что и у фото, и ролик сразу
играет со звуком: `play()` вызывается прямо в обработчике нажатия — только так
звук разрешают iOS и встроенные браузеры мессенджеров. Если браузер всё же
откажет, ролик остаётся на постере, и его запускают кнопкой ▶ панели.

- **Панель** — нативная панель браузера у `<video controls>`: вид, кнопки,
  перемотку, звук и полноэкранный режим (на iPhone — системным плеером)
  обеспечивает браузер; атрибут `controls` никто не снимает, своих стилей у
  панели нет.
- **Листание**: в галерее, где рядом есть фото, ролик листается вместе с ними
  (стрелки окна, ←/→, свайп вне кадра ролика). К ролику, до которого
  долистали, файл заранее не грузится (`preload="none"`, подгружается только
  постер), и сам он не запускается — только по нажатию на кадр или на ▶ панели.
  При уходе с ролика и при закрытии окна он останавливается, загрузка
  обрывается. Одновременно играет не больше одного ролика.
- **Клавиши и жесты на ролике — его**: пробел ставит на паузу, стрелки и
  Home/End перематывают, свайп по кадру — перемотка, а не листание.
- **Полноэкранный режим** включается кнопкой панели. Первый Esc выходит из
  него (окно остаётся, ролик играет), второй закрывает окно; фокус
  возвращается на плитку.
- **Не загрузился** — вместо кадра сообщение «Не удалось загрузить видео.».
- **Без JavaScript** плитка ведёт на файл: браузер открывает ролик своим
  плеером, «Назад» возвращает на страницу.

Своими стилями оформлены плитка (значок — токены `--media-play-size`,
`--media-play-icon-size`, цвета оверлея; секция 5 `app.css`) и кадр в окне
(секция 8).

## 9. Заголовки, приватность, индексация

Сборка пишет `dist/_headers` (синтаксис Cloudflare Pages):

```
/*
  X-Robots-Tag: noindex, nofollow
  Referrer-Policy: no-referrer
  X-Content-Type-Options: nosniff
  X-Frame-Options: DENY
  Content-Security-Policy: default-src 'self'; style-src 'self'; img-src 'self' data:; media-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'none'
/i/*
  Cache-Control: private, no-cache
```

и `dist/robots.txt` с `Disallow: /`. Мета-теги `robots` и `referrer` в
`template.html` и `stub.html` дублируют заголовки — на случай хостинга, который
не понимает `_headers`. Карта сайта не создаётся.

CSP работает потому, что страница по построению не нуждается в послаблениях:
все скрипты и стили — отдельные файлы из `/assets/`, inline-скриптов нет,
встраиваемых виджетов и карт нет, единственные внешние адреса — ссылки на
картографические сервисы, которые открываются по нажатию. Стили — только
файлы: `style-src 'self'` без `'unsafe-inline'`. В собранных страницах нет ни
атрибутов `style`, ни элементов `<style>` (это проверяет тест), а стили,
которые скрипт ставит во время работы (ширина скрытой полосы прокрутки при
открытом окне просмотра, пропорция кадра ролика в нём), задаются через CSSOM
(`element.style.setProperty`), и CSP их не ограничивает. Поэтому в разметке и
в скриптах нельзя писать `style="…"` и `setAttribute('style', …)`: браузер
такой стиль не применит. Скриптам (`script-src`) никаких послаблений тоже не
нужно.

Что ещё сделано ради приватности:

- в адресах и именах файлов нет персональных данных. `<title>`, `og:title` и
  `og:image:alt` страницы — «Приглашение · <имена пары>», описание — общий
  текст, картинка превью — титульник (имена, дата основного события, фото):
  **осознанное решение владельцев** — всё это одинаково у всех гостей и не
  содержит ничего о конкретном госте (ни обращения, ни приписок, ни токена).
  Заглушка — «Страница не найдена», без тегов превью;
- все ссылки в мета-тегах — пути от корня, `og:url` нет: адреса сайта в
  выводе сборки нет никогда ([2.5](#25-превью-ссылки-site_name-без-адреса-сайта));
- `robots.txt` запрещает обход (`Disallow: /`), поэтому X (Twitter) карточку
  не построит; Telegram и WhatsApp заголовок уже показывают — если они
  перестанут показывать превью, это отдельная правка;
- всё, что гостю не показано (секции, виджеты, события, приписки других
  гостей), вырезается до рендера: этого нет в HTML его страницы;
- календарные файлы — по одному на событие для всего сайта, без обращения и
  приписок, в каталоге медиа под хэшем содержимого с ключом из всех токенов;
  ссылка на файл есть только у гостей, которым событие видно, а вычислить имя
  без всех токенов нельзя — файл защищён так же, как страницы гостей
  ([5](#5-что-получается-в-dist-и-что-проверяется)). Общего файла со
  всеми событиями нет — он выдал бы скрытые события;
- заглушка одинакова для корня и для любого неверного пути и не намекает на
  структуру ссылок;
- медиа лежат в каталоге со случайным именем и публикуются под хэшами
  содержимого: файл секции, показанной одному гостю, не найти по имени;
  медиа, которые не показаны ни на одной странице, не публикуются;
- подтверждение участия происходит вне сайта: форм, `mailto:`/`tel:`-ссылок,
  телефонов и ников на страницах нет (внешние ссылки, кроме карт, запрещены
  проверкой сборки);
- команда `links` — единственная, печатающая персональные данные, — отказывается
  работать в CI ([2.4](#24-links--ссылки-для-рассылки)).

## 10. Непрерывная интеграция

`.github/workflows/ci.yml` запускается на каждый push и pull request (и вручную),
работает без секретов и ничего не выкладывает. Матрица — Python 3.10, 3.11,
3.12, 3.13; сторонние actions закреплены по SHA коммита; права `contents: read`.

Шаги и как повторить их у себя:

| Шаг CI | Локально |
|---|---|
| гигиена репозитория: под контролем версий нет медиа (проверяются все файлы, без исключений), нет результатов сборки, в именах файлов нет переводов строк | `git -c core.quotePath=false ls-files \| grep -Ei '\.(png\|jpe?g\|webp\|gif\|avif\|mp4\|mov\|webm\|ico\|svg)$'` |
| тесты | `python3 -m unittest` |
| Chrome есть на раннере (печать версии; нет — ошибка): им сборка рисует картинку превью | `google-chrome --version` |
| генерация медиа-заглушек (при необходимости ставится `ffmpeg`) | `python3 tools/gen_example_media.py` |
| проверка и сборка основного примера (с `SITE_NAME=Example`) | `python3 build.py validate && SITE_NAME=Example python3 build.py build --out /tmp/dist` |
| проверка и сборка примера без площадки и медиа | `python3 build.py build --data examples/data-venue-pending --media examples/media-none --out /tmp/dist-pending` |
| теги превью ссылки на страницах основного примера: `og:image` — `/assets/<mediaDir>/<хэш>.jpg`, файл — JPEG 1200×630 не больше 300 KB, по `/assets/og.*` ничего нет, есть `og:site_name`, нет `og:url`, нет `://` в `<meta>`; в заглушке тегов превью нет | `grep -o '<meta property="og:[^>]*>' /tmp/dist/i/*/index.html` |
| проверка результата: `index.html` = `404.html`, есть `_headers` и `robots.txt`, нет `*.json`, `*.map`, файлов витрины и страницы-превью, число страниц равно числу приглашений | `cmp /tmp/dist/index.html /tmp/dist/404.html` |
| воспроизводимость: две сборки подряд дают одинаковые контрольные суммы | собрать дважды в разные каталоги и сравнить `sha256` файлов |
| рабочее дерево осталось чистым | `git status --porcelain` |

Последний прогон на `main` — успешный на всех четырёх версиях Python; текущее

### 11.1. Что нужно проверить на настоящих устройствах

Автоматически это не проверяется — нужен живой телефон и реальные приложения:

1. **Видео** — воспроизведение, перемотка, звук и полноэкранный режим в iOS
   Safari, Android Chrome и во встроенных браузерах мессенджеров (Telegram,
   WhatsApp): именно там чаще всего открывают ссылку. По пунктам:
   - нажатие на плитку открывает окно, и ролик **сразу играет со звуком**, не
     на весь экран; пауза касанием, перемотка по дорожке; свайп по кадру не
     листает, стрелки окна листают;
   - кнопка «на весь экран»: на iPhone открывается системный плеер — это
     ожидаемо; после «Готово» снова окно, панель в порядке; закрытие окна
     останавливает звук;
   - в Telegram и WhatsApp на iPhone ролик может сразу открыться системным
     плеером (настройка приложения) — после выхода должно быть окно;
   - Android: «Назад» в полноэкранном режиме выходит из него, второй «Назад»
     закрывает окно; поворот экрана в полноэкранном режиме;
   - ролик, до которого долистали, сам не стартует и до нажатия не
     загружается; одно касание по его кадру или по ▶ запускает его (один раз,
     без мгновенной паузы); уход с играющего ролика обрывает звук;
   - без JavaScript (выключить в настройках Safari) плитка открывает ролик
     системным плеером, «Назад» возвращает на страницу;
   - VoiceOver / TalkBack: плитка читается как «Видео», окно — «Просмотр
     видео», после закрытия фокус — на плитке.
2. **Системный размер текста** — «Настройки → Экран и яркость → Размер текста»
   на iOS (в том числе режим «Увеличенный текст») и «Размер шрифта» на Android:
   страница должна следовать настройке, не давая горизонтальной прокрутки.
   Отдельно стоит посмотреть таймер и программу дня — они меняют раскладку по
   месту.
3. **Ландшафтная ориентация** телефона на обложке, на плитке видео и в окне
   просмотра: вертикальный ролик виден целиком вместе с панелью.
4. **Принудительное затемнение** во встроенном браузере (тёмная тема
   мессенджера): страница должна остаться в своей теме.
5. **Предпросмотр ссылки** — на выложенном сайте (адрес сборке не передаётся:
   `og:image` — путь от корня, `og:url` нет, см.
   [2.5](#25-превью-ссылки-site_name-без-адреса-сайта)):
   1. **Telegram на iOS и Android**: ссылка в «Избранное» — название сайта
      (или домен), «Приглашение · <имена>», описание; **есть ли
      картинка-титульник и крупная ли она** — записать; обращения гостя нет;
      у двух гостей карточки одинаковы. Кэш: после выкладки отправить ссылку
      [@WebpageBot](https://t.me/webpagebot); старые сообщения могут сохранить
      прежнюю карточку;
   2. **WhatsApp** (Android и iOS), **iMessage**, по возможности **X** — то же.
      Главный риск: относительный `og:image` и отсутствие `og:url` — записать
      по каждому мессенджеру, показана ли картинка; обходов не делать, при
      отсутствии картинки — вопрос владельцам;
   3. нет картинки — проверить её вес и что `/assets/<mediaDir>/….jpg`
      открывается по прямой ссылке; нет и заголовка — вероятна блокировка
      `robots.txt`;
   4. заглушка — превью без имён и картинки;
   5. начертание имён на картинке — совпадает ли со страницей на iPhone
      (вопрос шрифтов, [6.7](#67-иконка-картинка-предпросмотра-и-цвет-интерфейса-браузера)).
6. **Кнопки карт** — открываются ли ссылки в установленных приложениях карт.
7. **Календарь** — добавляется ли событие по кнопке «Добавить в календарь» на
   iOS и Android.
8. **Вкладки событий** на странице гостя с несколькими событиями:
   - выбрана актуальная вкладка — первостепенное событие гостя, пока оно не
     закончилось, потом ближайшее следующее, после всех — последнее; у
     прошедших событий пометка «прошло», у идущего — «идёт сейчас» (проверить
     в день праздника или переведя часы телефона);
   - касание вкладки показывает её карточку, и больше вкладка сама не
     переключается; при системном шрифте 200 % вкладки встают столбиком;
   - на десктопе с клавиатуры: Tab приходит на выбранную вкладку, стрелки
     (по кругу), Home и End переключают вкладки, следующий Tab уводит в
     карточку; VoiceOver / TalkBack читают «вкладка, выбрано» и пометку.
9. **Заглушка** на самом хостинге: корень и заведомо неверный путь должны
   отдавать одну и ту же страницу.
10. **Сворачивание обложки в верхнюю панель** — на iPhone с iOS 26 (там его
    ведёт CSS) и с iOS 17/18 (там — скрипт), в Safari и во встроенном браузере
    Telegram, и в Android Chrome:
    1. открыть приглашение (лучше с фото на обложке): текст обложки читается,
       панели не видно;
    2. медленно прокрутить: фото плавно тонет в вуали, имена и дата гаснут;
       когда от обложки остаётся полоса, в ней «Имена · дата», панель
       прилипает к верху и остаётся там; нет скачков и миганий;
    3. то же быстрыми бросками: в конце броска панель на месте; прокрутка
       вверх — обложка разворачивается обратно;
    4. повернуть телефон на середине страницы: панель у верха, не шире экрана,
       не под вырезом; на iOS 26 посмотреть, как Safari подкрашивает строку
       состояния под панелью;
    5. коснуться строки состояния (прокрутка наверх): обложка развёрнута,
       панели не видно. Страницу прокручивает `body`, а iOS по этому касанию
       прокручивает наверх только сам документ — если не сработает, записать
       (п. 12);
    6. открыть фото в галерее: окно поверх панели; после закрытия панель на
       месте;
    7. «Универсальный доступ → Движение → Уменьшение движения»: обложка не
       меняется при прокрутке, панель появляется сразу, когда обложка ушла;
    8. самый крупный системный «Размер текста»: панель выше, имена с «…»,
       дата целиком; в ландшафте панель заметно выше (около пятой части
       экрана) — оценить, не мешает ли;
    9. **верхний край после сворачивания** — на iPhone с iOS 26 и с iOS 18, в
       Safari и во встроенном браузере Telegram: между верхним краем экрана и
       панелью нет полосы, сквозь которую видно прокручиваемый текст
       страницы; вся область над панелью (строка состояния, вырез, шапка
       Telegram) — цвета панели, в том числе на странице с фото на обложке и
       в конце быстрого броска. На обложке с фото фото не пропадает раньше,
       чем проявилась панель. Шапка Telegram сама чуть светлее и нейтральнее
       панели — это её материал, не дефект страницы
       ([6.7](#67-иконка-картинка-предпросмотра-и-цвет-интерфейса-браузера)).
11. **Цвет над страницей и за её краями**
    ([6.7](#67-иконка-картинка-предпросмотра-и-цвет-интерфейса-браузера)):
    1. **Telegram на iOS** — открыть приглашение из чата. Ожидаемо: потянуть
       страницу вниз за верхний край, пока обложка развёрнута, и вверх за
       нижний край — открывшаяся область цвета панели. Над свёрнутой панелью
       обложки, под шапкой Telegram, **нет** текста страницы — только цвет
       панели (прокручивает `body`, см.
       [6.10](#610-как-проверять-стилизацию)); проверить при развёрнутой и
       при свёрнутой шапке Telegram (прокрутка вниз и вверх), с версиями iOS и
       Telegram. Сама шапка чуть светлее и нейтральнее панели: её цвет задаёт
       Telegram (стеклянный материал, `theme-color` и фон страницы он не
       читает) — известное ограничение, не исправляется;
    2. **Telegram на Android** — то же. Ожидаемо: перетягивание за край — цвет
       панели обложки; верхняя панель браузера Telegram — цвета его темы (при
       включённом адаптивном цвете — цвета панели обложки, см.
       [6.7](#67-иконка-картинка-предпросмотра-и-цвет-интерфейса-браузера));
    3. **Android Chrome** — адресная строка и строка состояния цвета панели и
       при развёрнутой, и при свёрнутой обложке; перетягивание за край — цвет
       панели;
    4. **заглушка** (корень сайта) — адресная строка обычного цвета, за
       краями — белый фон, как раньше.
12. **Прокрутка `body` вместо документа на сенсорном экране**
    ([4.7](#47-фрагменты-секций-и-виджетов)) — побочные эффекты, которые
    headless Chrome не показывает; по каждому записать, как есть, с версией
    iOS / браузера (на десктопе прокручивается документ, как раньше):
    1. **Safari на iPhone** (iOS 18 и 26): сворачивается ли адресная строка
       (панель вкладок) при прокрутке вниз. Safari сворачивает её по прокрутке
       самого документа, поэтому, вероятно, она останется развёрнутой;
       прокрутка при этом плавная, с инерцией и «резинкой» у краёв;
    2. **Android Chrome** — то же про адресную строку;
    3. **касание строки состояния** на iPhone — прокручивает ли наверх
       (п. 10.5);
    4. **позиция после перезагрузки** страницы и после «Назад» с другой
       страницы (карты, календарь): браузер сам восстанавливает только
       прокрутку документа, поэтому после перезагрузки страница, вероятно,
       откроется с начала; «Назад» из кэша страниц (обычно Safari) позицию
       сохраняет;
    5. **окно просмотра фото**: пока оно открыто, страница под ним не
       прокручивается ни пальцем, ни «резинкой»; после закрытия — на том же
       месте;
    6. **десктоп с клавиатуры** (Chrome, Safari, Firefox): сразу после
       открытия страницы, ничего не нажимая мышью, «Пробел», PageDown,
       стрелки и End прокручивают страницу; перезагрузка сохраняет позицию;
    7. **смешанные устройства** — режим выбирает основное устройство ввода
       (`pointer`): ПК с сенсорным экраном и мышью — вероятно, прокрутка
       документа; iPad с клавиатурой (и трекпадом) — прокрутка `body`. На
       iPad с клавиатурой проверить «Пробел» и стрелки сразу после открытия:
       если не прокручивают, пока не коснёшься страницы, — записать.
